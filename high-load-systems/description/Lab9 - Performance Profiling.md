# **ЛАБОРАТОРНА РОБОТА № 9 Тема: Профілювання продуктивності (Performance Profiling) та Діагностика вузьких місць (Bottleneck Diagnostics)** 

#### **1. Мета роботи** 

На основі результатів навантажувального тестування (Лабораторні роботи № 5–8) провести інструментальну діагностику системи та виявити підтверджене джерело деградації продуктивності (Root Cause). Опрацювати повний цикл інженерного аналізу: _Symptom → Hypothesis → Instrumentation → Evidence → Root Cause → Optimization → Regression Verification_ . 

По завершенню роботи студенти повинні вміти: 

- застосовувати системні інструменти профілювання CPU, Memory та I/O (JFR, AsyncProfiler, VisualVM, pprof, py-spy, dotnet-trace); 

- аналізувати плани виконання запитів СУБД (EXPLAIN ANALYZE) та виявляти неефективне виконання (Full Table Scan, Temp Tables, N+1 Problems); 

- використовувати засоби розподіленого трасування (OpenTelemetry / Jaeger / Zipkin) для декомпозиції затримок складних запитів; 

- аналізувати стан пулів з'єднань (Connection Pool Exhaustion) та тиск на прибиральник сміття (GC Allocation Pressure / Memory Leaks); 

- проводити контрольований повторний експеримент (A/B Testing) для підтвердження ефекту оптимізації та оцінки побічних ефектів (Trade-offs / Regression Effect). 

## **2. Завдання та етапи виконання** 

### **2.1. Фіксація симптому та формування гіпотез** 

1. Обрати проблемний сценарій з попередніх робіт із зафіксованими відхиленнями (наприклад, високий p99 Latency, Saturation, Lock Contention, GC Pause, Memory Leak). 

2. Сформулювати **не менше 2–3 перевірюваних гіпотез (H1, H2, H3)** щодо причин деградації продуктивності. 

### **2.2. Інструментальне профілювання (CPU, Memory & DB Profiling)** 

1. Подати контрольоване навантаження та зняти метрики за допомогою профілювальника: 

   - **CPU Profiling:** виявлення "гарячих" шляхів виконання (Hot Code Paths), надлишкової серіалізації, синхронізаційних блокувань. 

   - **Memory Profiling:** аналіз темпів виділення пам'яті (Allocation Rate), частоти зупинок GC та перевірка на наявність витоків пам'яті (Heap Dump Analysis). 

   - **Database Diagnostics:** виконання EXPLAIN ANALYZE для найдорожчих запитів, перевірка індексного покриття, виявлення проблем N+1 та затримок у Connection Pool. 

   - **Distributed Tracing:** декомпозиція загального часу відповіді (Total Latency) на 

складові сервісів, кешу та СУБД. 

2. Відкинути спростовані гіпотези та чітко зафіксувати докази (Evidence) для підтвердженої причини ( **Root Cause** ). 

### **2.3. Впровадження точкової оптимізації** 

Реалізувати цільову зміну, що безпосередньо усуває підтверджений Root Cause (додавання складеного індексу, оптимізація SQL, усунення N+1, рефакторинг алгоритму, зміна розміру Connection Pool / Allocation Strategy).

## **4. Порядок захисту та критерії оцінювання** 

### **Процедура захисту:** 

1. **Презентація проблеми та гіпотез:** Пояснення обраного симптому та сформульованих гіпотез H1–H3. 

2. **Демонстрація доказів (Evidence):** Показ у профілювальнику або плані виконання запиту (Flame Graph / EXPLAIN ANALYZE) конкретної точки відмови/уповільнення. 

3. **Live-демонстрація оптимізації:** Показ зміненого коду/конфігурації та виконання повторного тесту під навантаженням із порівнянням метрик. 

4. **Теоретичний захист:** Пояснення різниці між симптомом та причиною (Symptom vs Root Cause); принципів дії CPU Profiling (Sampling vs Instrumentation); оптимізації баз даних та аналізу ресурсних компромісів. 

### **Критерії оцінювання:** 

- **Доказовість аналізу:** Обґрунтування причини деградації лише на основі об'єктивних метрик інструментів профілювання. 

- **Цільова якість оптимізації:** Безпосередня відповідність внесених змін виявленій фундаментальній причині. 

- **Глибина розуміння системних компромісів:** Здатність оцінити побічний ефект оптимізації для інших модулів системи.
