# Лабораторна робота №2

Вимірювана модель якості ISO/IEC 25010: Performance Efficiency та Resilience Engineering

Проєкт: Relativa. Об’єкт вимірювання — читання графа `GET /graph/api/v1/graph`.

Сирі логи прогонів лежать у [lab2/evidence](evidence).

## Характеристика об’єкта дослідження

Обрана операція — `GET /api/v1/graph?organizationId={id}` сервісу Graph. Через Gateway вона доступна як `GET http://localhost:8080/graph/api/v1/graph?organizationId=1`. Операція будує вузли та ребра графа для автентифікованого користувача в організації і збагачує вузли угод оцінками ML (closure score, churn score). Типовий запит — GET з заголовком `Authorization: Bearer`. Очікувана успішна відповідь — HTTP 200 і JSON із масивами `nodes` та `edges`.

Час виконання залежить від PostgreSQL (читання користувача, робочих просторів, сутностей і зв’язків) і від зовнішньої залежності: RPC-оцінювання угод у ML через RabbitMQ. Клієнт — `RabbitMqMlScoringClient`. Він публікує запит в exchange і чекає відповідь у тимчасовій черзі. Якщо споживач ML не відповідає, без захисту очікування обривається таймаутом.

Технологічний стек: .NET 10, Gateway (YARP), Graph, PostgreSQL 16, RabbitMQ 3.13, ML (Django). Локальний запуск: Docker Desktop і `docker compose up` для postgres, rabbitmq, migration, auth, core, graph, ml, audit, gateway. Демо-вхід сіду — `admin@relativa.com`.

Інструмент навантаження: Grafana k6 2.2.0 (`k6.exe v2.2.0`, windows/amd64). Сценарій — [lab2/k6/graph-read.js](k6/graph-read.js).

## Performance Testing та валідація SLO

### Команда запуску

З каталогу репозиторію, коли Gateway відповідає на `http://localhost:8080`:

```text
k6 run -e PROFILE=normal lab2/k6/graph-read.js
k6 run -e PROFILE=elevated lab2/k6/graph-read.js
k6 run -e PROFILE=normal -e P95_MS=1 lab2/k6/graph-read.js
```

`setup()` логіниться через Gateway і бере перший `organizationId`. Далі віртуальні користувачі викликають лише читання графа. Поріг k6 `p(95)` і `http_req_failed` самі ставлять PASS або FAIL: ненульовий код виходу (у цьому прогоні 99) означає FAIL. Ручний підрахунок не потрібен.

### Модель навантаження

| Профіль | Зростання | Утримання | Віртуальні користувачі |
|---|---|---|---|
| normal | 10 с | 20 с, потім спад 5 с | до 5 |
| elevated | 10 с | 20 с, потім спад 5 с | до 40 |

Один сценарій, одні й ті самі тестові дані (організація сіду, id = 1). Різниця лише в інтенсивності.

### Обґрунтування порогів

Калібрування — normal, пороги навмисно розсунуті (`P95_MS=60000`), щоб зняти базову лінію, а не відсікти її. Виміряний p95 = 898,7 мс. Це інтерактивне читання графа: користувач чекає картину зв’язків, і відповідь уже біля однієї секунди через з’єднання з PostgreSQL і RPC до ML.

Прийнятний p95 узятий не як кругле число, а як потрійна базова лінія із підлогою 500 мс:

`max(500, 898,7 × 3) = 2700 мс`

Запас утричі відокремлює звичайний джиттер локального стенда від справжнього простою. Незахищений таймаут ML у 2000 мс плюс робота з базою вже не вміщається в комфортну відповідь і в експерименті відмови дає HTTP 504. Error rate < 1 % (`0.01`): читання графа не повинно масово завершуватися помилкою; поодинокий обрив з’єднання ще в межах бюджету, серія відмов — ні.

### Аналіз

FAIL викликав поріг p95, не частка помилок. Error rate у контрольному прогоні лишився 0 %. Виміряний p95 був 1053,7 мс, а поріг стояв 1 мс, тому k6 завершився з кодом 99. Сервіс при цьому відповідав. Так перевіряється сам механізм PASS/FAIL, а не випадкове падіння стенда.

Підвищений профіль показує справжній зсув. p95 виріс з 808 мс до 1279 мс, RPS — з 5,73 до 26,70, error rate — з 0 % до 0,58 % (обриви з’єднання з Gateway). Обидва пороги ще виконані, тому elevated лишається PASS. Вузьке місце на цьому стенді — час відповіді читання графа під більшою кількістю паралельних запитів, а не відмова залежності: частка помилок далеко від 1 %, затримка зростає разом із конкуренцією за PostgreSQL і RPC.

Середній час не замінює p95/p99. У elevated середнє 1114 мс, а p99 — 1468 мс. Середнє зміщують швидкі відповіді і воно не показує хвіст, у якому сидить помітна частка користувачів. Поріг на середньому може бути зеленим, коли кожен двадцятий запит уже помітно повільніший. Тому SLO стоїть на p95, а p99 лишається в журналі як контроль хвоста.

## Fault Injection та Resilience Engineering

### Залежність і спосіб відмови

Залежність — ML scoring через RabbitMQ RPC. У нормальному режимі Graph публікує список id угод і отримує оцінки. Якщо контейнер ML зупинений, брокер і Graph живі, але відповіді на RPC немає. Це таймаут залежності, а не вимкнення всього застосунку.

Команда відмови: `docker stop relativa-ml`. Після замірів контейнер знову запущений (`docker start relativa-ml`).

Політика зібрана в `ResilientMlScoringClient`. Сирий RPC-клієнт більше не ковтає збій: таймаут, недоступний брокер і помилкова відповідь пробрасуються далі. `GraphDataService` теж більше не ховає виняток, тож без декоратора `TimeoutException` доходить до `GraphGlobalExceptionHandler` і стає HTTP 504.

Параметри в `MlScoringResilience` (`appsettings.json`, для контейнера їх можна перекрити змінними `MlScoringResilience__*`):

| Параметр | Значення | Навіщо |
|---|---:|---|
| Enabled | true | Дефолт після впровадження захисту |
| MaxAttempts | 3 | Стеля повторів, щоб не було retry storm |
| PerAttemptTimeoutMs | 200 | Короткий бюджет однієї спроби |
| BaseDelayMs | 50 | Перша пауза backoff |
| MaxDelayMs | 400 | Стеля паузи |
| UnprotectedTimeoutMs | 2000 | Одна спроба в режимі «до», коли Enabled=false |

Backoff: 50 мс після першої невдачі, 100 мс після другої. Пауза рахується як `min(MaxDelay, BaseDelay × 2^(n-1))`.

Нескінченні синхронні повтори без паузи погіршують і так перевантажену залежність: кожен клієнтський запит множить навантаження на брокер, який уже не встигає відповідати. Обмеження тут такі: не більше трьох спроб, пауза між ними, окремий таймаут спроби, і скасований викликом запит далі не повторюється.

### До

`MlScoringResilience__Enabled=false`. Одна спроба, таймаут 2000 мс, виняток не ковтається.

Журнал: [fault-before.txt](evidence/fault-before.txt). Тіло відповіді: [fault-before.txt.body](evidence/fault-before.txt.body).

Після прогріву (перший запит після старту контейнера довший через прогрів EF):

- статус 504
- час 2,14 с
- тіло: Problem Details, `status: 504`, `detail: Timed out waiting for ML scoring RPC reply after 2000ms`
- лог Graph: `ML scoring RPC timed out after 2000ms`, далі `Handled Graph exception` і `System.TimeoutException`

Граф клієнту не віддається. Відмова ML стає відмовою всього запиту.

### Після

Той самий зупинений ML, `Enabled=true`. Три спроби по 200 мс, backoff, потім порожній словник оцінок і запис `ml_scoring_degraded`.

Журнал: [fault-after.txt](evidence/fault-after.txt).

Після прогріву:

- статус 200
- час 0,85 с
- лог: `ml_scoring_degraded attempts=3 reason=ML scoring attempt exceeded 200ms.`

Запит завершується контрольовано. Підсвітка угод відсутня, решта графа віддається. Каскадного 504 немає.

| | До | Після |
|---|---|---|
| Стан ML | контейнер зупинений | контейнер зупинений |
| Захист | вимкнений, 1 спроба, 2000 мс | 3 спроби, 200 мс, backoff 50/100 мс |
| HTTP | 504 | 200 |
| Час виміряного запиту | 2,14 с | 0,85 с |
| Реакція | TimeoutException, граф не побудовано | fallback без ML-оцінок, діагностичний лог |

## Автоматизована верифікація стійкості

Тест: `ResilientMlScoringClientTests` у `Graph/tests/Relativa.Graph.Integration.Tests`. Подвійник внутрішнього клієнта — NSubstitute. Затримка backoff — фіктивна `RecordingDelay`, тож тест не спить і не залежить від RabbitMQ, ML чи випадкового таймінгу. Клас уже входить у `dotnet test` цього проєкту і в job CI `Graph — Integration Tests`.

Перевірки:

- успішна відповідь залежності: рівно один виклик, оцінка на місці, лога `ml_scoring_degraded` немає, fallback не вмикався;
- два таймаути і третя успішна спроба: рівно три виклики, оцінки повернені, паузи 50 мс і 100 мс;
- усі спроби падають: рівно три виклики, порожній словник, у логу є `ml_scoring_degraded` і `attempts=3`;
- скасований токен виклику: один виклик і виняток скасування, без додаткових спроб і без fallback.

Фрагмент перевірки повної відмови:

```csharp
var result = await Build(inner, delay, logger).ScoreBatchAsync([1, 2]);

result.Should().BeEmpty();
await inner.Received(3).ScoreBatchAsync(Arg.Any<IReadOnlyList<int>>(), Arg.Any<CancellationToken>());
delay.Delays.Should().HaveCount(2);
logger.Messages.Should().Contain(m => m.Contains("ml_scoring_degraded", StringComparison.Ordinal)
                                      && m.Contains("attempts=3", StringComparison.Ordinal));
```

Три послідовні запуски однією командою:

```text
dotnet test Graph/tests/Relativa.Graph.Integration.Tests/Relativa.Graph.Integration.Tests.csproj --filter FullyQualifiedName~ResilientMlScoringClientTests
```

## Висновок

Характеристика Performance Efficiency (time behaviour) для читання графа зафіксована числовим SLO: p95 ≤ 2700 мс і error rate < 1 %. Поріг виведений з виміряної базової лінії 899 мс, а не обраний довільно. k6 сам ставить PASS на нормальному профілі й FAIL, коли поріг p95 занижений до 1 мс. Підвищене навантаження зсуває p95 і RPS, але лишається в межах SLO. p95 і p99 потрібні окремо від середнього, бо хвіст повільніший за середнє.

Характеристика Reliability (fault tolerance) закрита обмеженим retry і fallback. Таймаут ML без захисту перетворює весь запит графа на HTTP 504. З захистом той самий збій дає HTTP 200, три спроби, паузу між ними і діагностичний лог `ml_scoring_degraded`. Автотест із підставним клієнтом тричі поспіль підтверджує і успішний шлях, і вміст fallback, і кількість спроб, і відсутність повтору після скасування.
