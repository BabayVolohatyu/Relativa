ЛАБОРАТОРНА РОБОТА №7
Інформаційна складність за Чепіним та автоматизоване виявлення 
критичних зон (Hotspots) у хмарному CI/CD

Мета роботи: Набути практичних навичок проведення інформаційного семантичного аудиту програмних систем за методологією Неда Чепіна; навчитися проводити контурний аналіз використання даних та класифікувати внутрішні змінні програми за їхніми функціональними ролями (P, M, C, T); опанувати інженерні практики оптимізації інформаційної складності через впровадження принципів незмінності об'єктів (Immutable Data) та паттерну об'єктів-значень (Value Objects); навчитися проєктувати та впроваджувати автоматизовані сценарії збору метрик якості у хмарних CI/CD пайплайнах розгортання софту; розробити та практично застосувати аналітичну матрицю виявлення критичних зон (Hotspots) кодової bases на основі синергетичного поєднання статичних мір складності алгоритмів та метрик динаміки процесу розробки з історії Git-репозиторію.

Інструментарій:
    • VCS Analytics Engine: Інструментарій командного рядка Git CLI (git log).
    • Cloud Orchestration Server: Платформа GitHub Actions (безкоштовні хмарні хвилини для публічних репозиторіїв) або GitLab CI/CD Free Tier.
    • CLI Static Analyzers (з минулих лаб): Lizard CLI або Radon CLI / TyphonJS Escomplex (для вивантаження звіту в машиночитаний JSON-формат).

Об'єкт дослідження: Індивідуальний програмний проєкт студента, який розвивається протягом семестру, або (для Завд.3) масштабний Enterprise Open-Source проєкт з GitHub обсягом від 50 методів та від 50 комітів в історії Git.


ПОРЯДОК ВИКОНАННЯ ЗАВДАНЬ

Завдання 1. Інформаційний семантичний аудит транзакційного модуля за Чепіним
Студент має провести ретельний контурний аудит використання даних у лінійному або транзакційному коді, де класичні топологічні метрики (Мак-Кейб) є «сліпими», та оцифрувати приховану інженерну заплутаність змінних, що загрожує стабільності системи при масштабуванні.

Покроковий алгоритм виконання:
    1. Вибір об'єкта семантичного аналізу та контурна класифікація:
Окремим методом обрати один критичний за архітектурною роллю алгоритм у своєму індивідуальному проєкті. Метод повинен належати до інтеграційного контуру (робота з платіжними шлюзами, сторонніми REST API, вебхуками) або бути лінійним методом, отриманим наприкінці ЛР№6 після впровадження Lookup Table. Критерій відбору: низька цикломатична складність (𝐶𝐶≤5), але інтенсивна робота з даними (прийом аргументів, оголошення внутрішніх станів, мапування об'єктів).
Провести ретельний аналіз тексту обраного методу. Виписати абсолютно всі змінні (включаючи вхідні аргументи, локальні об'єкти та службові ідентифікатори), які зустрічаються всередині методу, та розподілити їх за чотирма функціональними ролями Чепіна:
    •  (Вхідні): Змінні, які метод приймає «на вхід» як аргументи або зчитує з конфігурацій, і які використовуються виключно для пасивного читання в обчисленнях без жодної модифікації в тілі функції.
    •  (Модифіковані): Локальні або глобальні змінні, значення чи стан яких хоча б один раз перезаписується або трансформується під час виконання алгоритму.
    •  (Керуючі): Змінні, які безпосередньо використовуються в логічних умовах (if, while, switch) або керують бізнес-логікою прийняття рішень процесором у методі.
    •  (Транзитні): Змінні, які метод приймає ззовні або створює всередині лише для того, щоб без жодних змін прокинути (передати) як аргумент у виклик іншої підсистеми (іншу функцію чи метод). Наприклад, ID користувача, токен або DTO-об'єкт.

Застосування правила інженерного пріоритету: Якщо одна й та сама змінна виконує кілька ролей (наприклад, прийшла в аргументах як пасивне значення P, але далі перевіряється в блоці if), студент зобов'язаний присвоїти їй тип із найвищою інженерною вагою згідно з ієрархією: 𝐶𝑀𝑃𝑇.
    2. Формульний розрахунок складності: 
Підрахувати сумарну кількість змінних кожного типу та вирахувати підсумковий коефіцієнт інформаційної складності за фундаментальною формулою Чепіна:

На основі отриманого числа довести рівень ризику появи дефектів мутації. В Enterprise-стандартах для лінійних методів показник  є прямим індикатором архітектурного хаосу в даних додатка.

Очікуваний результат завдання №1 у звіті
    • Декларація об'єкта аналізу: Назва методу, його архітектурна роль у проєкті та початковий показник цикломатичної складності за Мак-Кейбом (доказ лінійності коду).
    • Семантична матриця Чепіна: Зведена таблиця аналізу змінних у такому форматі:
Назва змінної | Тип даних | Клас за Чепіним (P/M/C/T) | 
Коротке інженерне обґрунтування ролі
    • Формульний розрахунок складності: Покрокове підставлення значень у формулу Чепіна та фінальний індекс .


Завдання 2. Очищення інформаційного хаосу через принципи імутабельності (Immutable) та Value Objects
Студент має реалізувати повний інженерний цикл цілеспрямованого витискання мутабельного хаосу з коду додатка за допомогою суворих канонів Enterprise-архітектури.

Покроковий алгоритм виконання:
    1. Симуляція збою через неконтрольовану мутацію даних (FAIL-стан): 
Продемонструвати вразливість поточного коду до випадкових помилок при роботі зі змінними. 
    • Дія (Краш-тест): Додати в код методу (або написати у вигляді окремого unit-тесту) сценарій, де одна з модифікованих проміжних фінансових або логічних змінних типу M випадково перезаписується в ході обчислень через відсутність захисту від змін (мутабельність об'єкта).
    • Документально зафіксувати отримання невалідного бізнес-результату (наприклад, касовий розрив, коли знижка ресторану випадково перезаписала базову ціну, або збій логування подій), зафіксувавши стан FAIL окремим проміжним комітом у Git: feat(audit): simulate data mutation issue, FAIL.
    2. Архітектурний рефакторинг імутабельності (PASS-стан): 
Повністю переписати логіку аналізованого методу, ліквідувавши хаос змінних за допомогою двох індустріальних патернів:
    • Принцип Імутабельності (Immutable Data): Заборонити всім локальним та вхідним змінним змінювати свій стан. Перевести змінні у жорсткий режим «Тільки для читання» (const у JS/TS, final у Java, readonly у C# або спеціальні незмінні структури даних). Якщо дані потрібно змінити, замість перезапису старої змінної створюється новий об'єкт. Це повністю знищує небезпечні змінні типу  переводячи їх у безпечний тип .
    • Паттерн Об'єктів-Значень (Value Objects): Згрупувати хаотичні дрібні розрізнені змінні, які логічно пов'язані між собою (наприклад: сума, валюта та відсоток податку), в один єдиний незмінний об'єкт-контейнер. Це миттєво скоротить загальну кількість керуючих (C) та вхідних (P) сутностей у самому методі, перенісши логіку перевірок усередину компактного класу-контейнера.
    3. Повторна семантична верифікація за Чепіним: 
Провести повторний семантичний аналіз чистого коду. Скласти оновлену таблицю Чепіна та довести, що завдяки рефакторингу підсумковий показник інформаційної складності впав щонайменше удвічі, досягнувши безпечного еталону для чистих функцій . Зафіксувати успішний статус PASS комітом у Git: refactor(audit): reduce Chapin complexity using immutable Value Objects, PASS.

Очікуваний результат завдання №2 у звіті
    • Опис симуляції збою (FAIL): Лістинг коду або текстовий опис сценарію, де мутабельність даних призводить до помилки, та скріншот логів/тестів із зафіксованим збоєм.
    • Архітектурний опис рефакторингу: Пояснення того, як саме студент реалізував принципи імутабельності (наприклад, заміна ключових слів на const / final) та які змінні були інкапсульовані в об'єкти-значення (Value Objects).
    • Порівняльна матриця коду (До/Після): Наочне зіставлення фрагментів вихідного та оптимізованого коду.
    • Нова матриця та формула Чепіна (PASS): Оновлена таблиця класифікації змінних, фінальний розрахунок індексу складності, який підтверджує падіння показника  у 2 або більше разів, та підтвердження успішного статусу PASS.
    • Git History: Скріншот дерева комітів, де зафіксовано перехід Simulated Mutation Issue (FAIL)  chapin weight reduction via value objects (PASS).


Завдання 3. Скриптування хмарного моніторингу та побудова синергетичної матриці критичних зон (Hotspots)
Студент піднімається на найвищий рівень архітектурного контролю (QA Governance) та автоматизує збір інженерних даних у хмарі, об'єднуючи статичні метрики коду з динамічними метриками історії Git розробки для мапування зон ризику.

Покроковий алгоритм виконання:
    1. Написання автоматизованого скрипту для CI/CD пайплайну: 
Розробити виконуваний сценарій автоматизації для хмарного сервера збірки (на вибір: YAML-конфіг для GitHub Actions, GitLab CI/CD, або універсальний скрипт Bash / PowerShell). Скрипт повинен виконувати такі автоматичні дії у хмарному раннері (в Docker-контейнері):
    • Автоматично інсталювати потрібний CLI-сканер складності під час кожного Push або Pull Request.
    • Запускати сканування всього репозиторію та експортувати детальний звіт у структурованому машиночитаному форматі (JSON або CSV).
    • Зберігати та експортувати цей звіт як хмарний артефакт збірки (Build Artifact).
    2. Збір метрик процесу розробки через Git CLI (Code Churn): 
Для побудови карти Hotspots студенту потрібні дані про інтенсивність роботи команди над файлами. Якщо власний репозиторій занадто малий (має коротку Git-історію), студент виконує це завдання одним із трьох способів:
Варіант 1. Ретроспективний аудит
Використати вже наявну історичну Git-історію проєкту з минулих семестрів для аналізу Churn Rate. Як це працює: Студент запускає команду git log для свого існуючого старого проєкту. Git витягує історію комітів з минулого року. Студент побачить, які файли він тоді міняв найчастіше (наприклад, файл з логікою бази даних мінявся 15 разів, а файл конфігурації – 1 раз). Далі він «напускає» CLI-сканер на цей готовий проєкт і зводить дані докупи. 
Варіант 2. Метод «Штучного наповнення історії»
Написання циклічного Bash (або PowerShell)-скрипту на 5 рядків, який вносить пусті коментарі та генерує серію з 10-15 комітів у обрані файли.
Варіант 3. Аудит відкритого Enterprise Open-Source проєкту
Виконання команди git clone великої світової бібліотеки з GitHub під свій стек обсягом від 50 методів та від 50 комітів, виступаючи у ролі зовнішнього аудитора. 

Студент запускає у терміналі кастомну аналітичну команду на базі git log, яка підраховує точну кількість модифікацій для кожного файлу проєкту за останній період (Churn Rate – 90 днів): git log --format=format: --name-only | egrep -v '^$' | sort | uniq -c | sort -nr
    3. Побудова та аналіз синергетичної матриці Hotspots (критичних зон): 
Об'єднати дані хмарного звіту CLI-сканера (складність алгоритмів за Мак-Кейбом/Холстедом) та дані інтенсивності з Git CLI в єдину аналітичну матрицю. Матриця має покривати щонайменше 5 ключових файлів індивідуального проєкту та розділяти їх на 4 категорії ризику:
    • High Risk (God Objects / Червона зона): Висока складність (CC>10) + висока мінливість у Git (багато комітів). Це головні Hotspots, які плодять регресійні баги та блокують паралельну розробку.
    • Sleeping Danger (Спляча загроза / Жовта зона): Висока складність + низька мінливість (код заплутаний, але його давно ніхто не редагував). Потребує рефакторингу лише при надходженні нових Change Requests.
    • Active Development (Активна зона / Зелена зона): Низька складність + висока мінливість (код постійно дописується, але архітектурно залишається чистим, лінійним та простим). Ідеальний стан розробки.
    • Stable Code (Стабільна зона / Сіра зона): Низька складність + низька мінливість. Стабільний утилітарний код.

Очікуваний результат завдання №3 у звіті
    • Код автоматизації CI/CD: Повний лістинг написаного конфігураційного файлу пайплайну (або Bash/PowerShell скрипту оркестрації) та скріншот успішного виконання збірки (Job Success) у хмарному інтерфейсі GitHub/GitLab з прикріпленим артефактом звіту.
    • Лог метрик процесу: Текст консольної команди Git та виведений терміналом список файлів проєкту, відсортований за кількістю комітів.
    • Синергетична матриця Hotspots: Заповнена таблиця аналізу для 5+ файлів проєкту за таким шаблоном:
Назва файлу | Метрика складності (CC або Effort) | Кількість комітів (90 днів) | 
Категорія ризику (Hotspot / Sleeping / Active / Stable)

    • 1.5 бали: Студент проаналізував занадто спрощений метод (де всього 1–2 змінні), або припустився помилок у класифікації ролей (наприклад, переплутав керуючі змінні C з транзитними T, через що фінальний розрахунок виявився невалідним.
    • 0 балів: Завдання не виконано, або класифікація Чепіна повністю відсутня.
Завдання 2 – 4 бали:
    • 4 бали: Сценарій збою мутації (FAIL) задокументовано чітко. Рефакторинг проведено на високому рівні: повністю впроваджено імутабельність та патерн Value Object. Інформаційна складність за Чепіним знизилася щонайменше вдвічі, що доведено математично в оновленій матриці. Git-історія містить усі обов'язкові коміти станів.
    • 2 бали: Студент зменшив складність коду, але рефакторинг був формальним (просте винесення коду в інший метод через Extract Method, але змінні все одно залишилися мутабельними типу M, а логіка не захищена від збоїв). Або пропущено етап симуляції FAIL у Git.
    • 0 балів: Завдання не виконано, код залишився без архітектурних змін.
Завдання 3 – 3 бали:
    • 3 бали: Скрипт CI/CD автоматизації хмари написаний без помилок, успішно відпрацьовує у хмарі та генерує артефакт звіту (підтверджено логами). Команду Git для збору Churn Rate виконано коректно. Побудовано та глибоко проаналізовано матрицю критичних зон (Hotspots) з чітким управлінським обґрунтуванням пріоритетів рефакторингу на наступний спринт.
    • 1.5 бали: Студент написав локальний скрипт, але не зміг інтегрувати його у хмарний CI/CD пайплайн (немає логів запуску у хмарі). Або матриця Hotspots побудована «наосліп» – без реальних динамічних даних з історії Git-логу.
    • 0 балів: Завдання не виконано, автоматизація та Hotspot-аналітика відсутні.

Штрафні бали (при захисті у форматі Live Demo):
    • –2 бали: Студент не може усно пояснити інженерний зміст «ваги» кожного типу змінних за Чепіним або плутає поняття мутабельності та імутабельності об'єктів.
    • –3 бали: Порушено Регламент взаємодії з ШІ (лог діалогу відсутній, або ШІ виконав роботу та класифікацію замість студента).
