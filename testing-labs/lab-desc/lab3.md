Інженерія якості та супровід програмних систем 
ЛАБОРАТОРНА РОБОТА №3 
Maintainability Refactoring та 
Software Supply Chain Security 
Мета роботи: набути практичних навичок цілеспрямованого рефакторингу коду на основі 
вимірюваних показників підтримуваності; інтеграції засобів Software Composition Analysis для 
виявлення ризиків у сторонніх компонентах; налаштування автоматизованого контролю 
секретів і запобігання потраплянню конфіденційних даних до репозиторію. 
Загальна постановка завдання 
У межах лабораторної роботи необхідно реалізувати комплекс технічних заходів, 
спрямованих на покращення характеристики Maintainability моделі якості ISO/IEC 25010 та 
зниження ризиків програмного ланцюга постачання (Software Supply Chain Security). 
Для виконання роботи студент використовує програмний проєкт із Лабораторної 
роботи №1 або №2. Проєкт повинен містити достатній обсяг власного коду для аналізу 
складності, декларацію сторонніх залежностей і Git-репозиторій, у якому можна безпечно 
виконати контрольовану перевірку механізму виявлення секретів. 
У результаті виконання роботи має бути реалізований повний цикл вимірювання, 
усунення та автоматизованої перевірки ризиків: 
Аналіз складності → Рефакторинг → Повторне вимірювання → 
SCA-сканування → CVE-тріаж → Усунення або обґрунтування ризику → 
Тестовий секрет → Блокування FAIL → Безпечна конфігурація → PASS 
ФОРМА ЗДАЧІ ТА ЗАХИСТУ РОБОТИ 
1. Формат та регламент захисту (Live Demo) 
Захист лабораторної роботи відбувається виключно під час практичного заняття у 
форматі живої демонстрації екрана викладачу. Оцінка виставляється за результатами 
демонстрації та відповідей на запитання. На захист одного студента відводиться до 5 хвилин. 
Усі аналізатори, залежності та Git hooks повинні бути налаштовані й готові до запуску до 
початку захисту. 
2. Етапи демонстрації (чеклист для студента) 
Під час захисту студент повинен продемонструвати викладачу три ключові артефакти: 
▪  Крок 1. Measurable Refactoring Diff. У Git History або IDE демонструється один і той 
самий метод чи клас «До» та «Після» рефакторингу. Студент показує числові значення 
Cognitive/Cyclomatic Complexity, результат автоматизованих тестів і пояснює, які 
техніки змінили структуру коду без зміни його бізнес-поведінки. 
▪  Крок 2. SCA Security Audit. У терміналі запускається npm audit, pip-audit, OWASP 
Dependency-Check, cargo audit, Snyk або аналогічний інструмент. Студент демонструє 
актуальний звіт, один детально розібраний CVE-кейс і результат повторного 
сканування після оновлення, заміни або документованого прийняття ризику. 
▪  Крок 3. Secrets Trap Demonstration. У спеціально підготовленому тестовому файлі 
створюється синтетичний секрет, після чого Gitleaks, TruffleHog або pre-commit hook 
повинен заблокувати коміт чи завершити перевірку зі статусом FAIL. Після 
перенесення значення до змінної середовища та очищення індексу Git повторна 
перевірка має завершитися статусом PASS. 
3. Умови успішного захисту 
▪  Якщо відсутні числові метрики «до/після» або не доведено збереження поведінки коду 
тестами, Завдання 1 не може бути оцінене максимальним балом. 
▪  Якщо SCA-сканер лише запускається, але студент не може пояснити джерело, 
критичність і спосіб обробки хоча б однієї вразливості, Завдання 2 вважається 
виконаним частково. 
Інженерія якості та супровід програмних систем 
▪  Для краш-тесту дозволено використовувати лише синтетичні або спеціально згенеровані 
тестові секрети. Реальні ключі, паролі чи токени не повинні потрапляти до файлів 
проєкту навіть тимчасово. 
ПОРЯДОК ВИКОНАННЯ 
Завдання 1. Вимірюваний рефакторинг коду 
Необхідно обрати структурно складну ділянку коду, виконати цілеспрямований 
рефакторинг і кількісно довести покращення підтримуваності без зміни функціональної 
поведінки системи. 
Для виконання завдання студент повинен: 
▪  Ідентифікувати проблемну ділянку. За допомогою SonarQube, SonarCloud, Qodana, 
IDE inspection або іншого аналізатора знайти метод чи клас із Cognitive Complexity > 15 
або Cyclomatic Complexity > 10. Якщо проєкт не містить перевищення, дозволено 
обрати об’єкт із найбільшим значенням і обґрунтувати необхідність оптимізації. 
▪  Зафіксувати baseline. Зберегти вихідний код, числові значення Cognitive Complexity, 
Cyclomatic Complexity, кількість рядків/гілок і, за наявності, Technical Debt. Створити 
окремий Git-коміт початкового стану. 
▪  Підготувати захисні тести. Перед структурними змінами переконатися, що поведінка 
обраного методу покрита автоматизованими тестами. За потреби додати щонайменше 
два тести для основного та граничного сценарію. 
▪  Розробити стратегію рефакторингу. Застосувати щонайменше дві доречні техніки, 
наприклад Extract Method, Guard Clauses, Replace Conditional with Polymorphism, 
Strategy Pattern, усунення дублювання або декомпозицію відповідальностей. Техніки 
мають відповідати фактичній проблемі, а не використовуватися формально. 
▪  Повторно виміряти метрики. Запустити той самий аналізатор і підтвердити зниження 
Cognitive Complexity до ≤ 15 або інше суттєве вимірюване покращення. Порівняння 
повинно виконуватися для тієї самої ділянки коду та за однаковою конфігурацією 
правил. 
▪  Провести регресійну перевірку. Запустити автоматизовані тести й підтвердити, що 
рефакторинг не змінив бізнес-логіку. У Git History повинні бути видимі окремі стани 
до і після рефакторингу. 
Результат виконання завдання: документований Code Review у форматі «до/після», 
успішний набір регресійних тестів і вимірюване зниження складності обраної ділянки коду. 
Завдання 2. Аналіз безпеки сторонніх компонентів 
Необхідно інтегрувати засіб Software Composition Analysis, сформувати профіль 
ризиків сторонніх залежностей і виконати технічний тріаж виявлених вразливостей. 
Для виконання завдання студент повинен: 
▪  Обрати та налаштувати SCA-інструмент. Використати засіб, сумісний із 
технологічним стеком проєкту: npm audit, pip-audit, OWASP Dependency-Check, cargo 
audit, Snyk або аналог. Зафіксувати назву, версію, команду запуску та аналізовані 
dependency/lock-файли. 
▪  Виконати первинне сканування. Отримати машинозчитуваний або HTML/текстовий 
звіт. Зафіксувати загальну кількість компонентів і розподіл виявлених вразливостей за 
рівнями Critical, High, Medium та Low. 
▪  Провести CVE-тріаж. Для щонайменше однієї вразливості рівня High/Critical, а якщо 
таких немає — для найвищої доступної, визначити CVE/Advisory ID, уразливу 
бібліотеку й версію, шлях потрапляння залежності (direct/transitive), потенційний вплив 
і наявність виправленої версії. 
▪  Обрати спосіб обробки ризику. Оновити або замінити залежність, виключити 
непотрібний транзитивний компонент чи документовано прийняти ризик із технічним 
Інженерія якості та супровід програмних систем 
обґрунтуванням і компенсувальним контролем. Ігнорування без пояснення не 
допускається. 
▪  Виконати повторне сканування. Порівняти звіти до і після змін, підтвердити 
зменшення кількості або критичності вразливостей та переконатися, що проєкт 
збирається і тести проходять успішно. 
▪  Забезпечити відтворюваність. Додати команду SCA-перевірки до документації, build 
script або CI-конфігурації так, щоб аудит можна було повторити без ручного 
налаштування інструмента. 
Результат виконання завдання: налаштована повторювана SCA-перевірка, сформований 
профіль ризиків залежностей, детальний CVE-тріаж і зафіксований результат усунення або 
обґрунтованої обробки вразливості. 
Завдання 3. Запобігання витоку секретів 
Необхідно налаштувати автоматичне виявлення секретів у кодовій базі та перевірити, 
що захисний механізм блокує небезпечну зміну до її потрапляння в історію репозиторію. 
Для виконання завдання студент повинен: 
▪  Інтегрувати secret scanner. Налаштувати Gitleaks, TruffleHog або pre-commit hook із 
чіткою командою запуску. Перевірка повинна охоплювати staged changes або весь 
репозиторій і повертати ненульовий код завершення при виявленні порушення. 
▪  Підготувати безпечний краш-тест. Створити лише синтетичне значення, яке 
відповідає тестовому шаблону токена чи пароля, у спеціальному файлі. Значення не 
повинно надавати доступу до реального сервісу або облікового запису. 
▪  Зафіксувати блокування. Додати тестовий файл до staging area та спробувати виконати 
коміт або запустити сканування. Інструмент повинен завершити перевірку зі статусом 
FAIL, вказати файл/рядок або правило та не допустити небезпечну зміну до 
репозиторію. 
▪  Усунути порушення. Видалити hardcoded secret із коду, перенести конфігураційне 
значення до Environment Variable або локального .env-файлу, додати локальний 
конфігураційний файл до .gitignore та надати безпечний .env.example без реальних 
значень. 
▪  Очистити Git-стан. Переконатися, що секрет відсутній у staged changes та історії 
комітів. Якщо тестове значення випадково було закомічено, видалити його з історії 
відповідним інструментом; будь-який реальний секрет у такій ситуації необхідно 
негайно відкликати та замінити. 
▪  Підтвердити PASS. Повторно запустити перевірку й отримати успішний статус. Додати 
secret scan до стандартного локального workflow або CI, щоб контроль автоматично 
виконувався для наступних змін. 
Результат виконання завдання: діючий автоматизований бар’єр, який виявляє синтетичний 
секрет, блокує небезпечну операцію зі статусом FAIL і успішно пропускає очищену 
конфігурацію зі статусом PASS. 
ВИМОГИ ДО ОФОРМЛЕННЯ ЗВІТУ 
Звіт повинен містити результати всіх етапів дослідження: 
Характеристика проєкту та інструментів 
▪  Призначення проєкту, технологічний стек, основні dependency-файли та спосіб запуску 
тестів. 
▪  Назви, версії та команди запуску аналізатора складності, SCA-сканера і secret scanner. 
Вимірюваний рефакторинг 
▪  Обґрунтування вибору методу/класу та baseline-метрики складності. 
▪  Лістинги або Git diff коду «До» та «Після», опис застосованих технік. 
▪  Порівняльні метрики та підтвердження успішного проходження тестів після змін. 
Інженерія якості та супровід програмних систем 
SCA Security Audit 
▪  Первинний і повторний звіти сканування із розподілом Critical/High/Medium/Low. 
▪  Таблиця: компонент, installed/fixed version, direct/transitive, CVE/Advisory ID, severity, 
рішення. 
▪  Детальний тріаж однієї вразливості та доказ працездатності проєкту після оновлення 
залежностей. 
Secrets Leak Prevention 
▪  Конфігурація інструмента або pre-commit hook без реальних секретів. 
▪  Скріншот/лог контрольованого FAIL із синтетичним секретом та успішного PASS після 
виправлення. 
▪  Фрагменти безпечної конфігурації: читання Environment Variable, правило .gitignore та 
.env.example.

КРИТЕРІЇ ОЦІНЮВАННЯ (максимум: 10 балів) 
Завдання 1. Measurable Refactoring — 3,5 бала 
PASS 
Без секретів 
▪  3,5 бала: Наведено коректний baseline, код «до/після» і числове порівняння метрик. 
Застосовано щонайменше дві доречні техніки рефакторингу, Cognitive Complexity 
знижено до ≤ 15 або отримано інше суттєве покращення, а незмінність поведінки 
підтверджено автоматизованими тестами. 
▪  2,5 бала: Рефакторинг і зниження метрик продемонстровано, але вибір технік пояснено 
поверхнево або тестове підтвердження охоплює не всі ключові сценарії. 
▪  1,5 бала: Код структурно змінено, проте числове покращення незначне, метрики 
виміряно різними інструментами/правилами або відсутній надійний baseline. 
▪  0,5 бала: Наведено лише косметичні зміни, перейменування чи форматування без 
вимірюваного впливу на підтримуваність. 
Завдання 2. SCA Security Audit — 3 бали 
▪  3 бали: SCA-інструмент інтегровано та його запуск відтворюється. Сформовано 
первинний профіль ризиків, виконано детальний CVE-тріаж, застосовано 
обґрунтований спосіб обробки ризику та наведено повторний звіт разом з успішною 
збіркою/тестами. 
▪  2 бали: Сканування і тріаж виконано, але відсутній повторний звіт або рішення щодо 
вразливості не підтверджене технічно. 
▪  1 бал: Наведено лише необроблений звіт чи скріншот без аналізу direct/transitive 
dependency, впливу та способу виправлення. 
▪  0 балів: SCA-перевірка не запускається або аналізує не той проєкт/набір залежностей. 
Завдання 3. Secrets Leak Prevention — 3,5 бала 
▪  3,5 бала: Secret scanner або hook інтегровано у workflow. Безпечний краш-тест із 
синтетичним секретом стабільно дає FAIL і блокує операцію; після винесення 
Інженерія якості та супровід програмних систем 
конфігурації до Environment Variables, налаштування .gitignore та очищення Git-стану 
перевірка завершується PASS. 
▪  2,5 бала: FAIL/PASS продемонстровано, але перевірка запускається лише вручну або 
безпечна конфігурація/.env.example оформлені неповно. 
▪  1,5 бала: Інструмент знаходить тестове значення, але не блокує commit/build через 
некоректний exit code або не охоплює staged changes. 
▪  0,5 бала: Є лише .gitignore чи ручний пошук рядків без автоматизованого механізму 
виявлення секретів. 
Штрафні бали (під час захисту) 
▪  –2 бали: студент не може пояснити різницю між Cyclomatic та Cognitive Complexity або 
пов’язати застосований рефакторинг зі зміною метрик. 
▪  –2 бали: CVE просто приховано через ignore/suppression без перевірки досяжності, 
строку дії винятку та технічного обґрунтування. 
▪  –3 бали: до репозиторію або звіту додано реальний секрет, токен чи пароль. Такий секрет 
необхідно негайно відкликати; відповідна частина роботи не зараховується до усунення 
інциденту.
