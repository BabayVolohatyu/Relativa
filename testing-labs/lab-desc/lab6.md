Топологічний та аналітичний аудит внутрішньої складності алгоритмів 
(метрики Холстеда та Мак-Кейба)

Мета роботи: Набути практичних навичок аналітичного та топологічного аудиту внутрішньої структури програмного забезпечення; навчитися інструментально збирати базові міри Холстеда та розраховувати уявні зусилля розробника для локалізації складних модулів; опанувати методику побудови керуючих графів потоку виконання (Control Flow Graph) та верифікації цикломатичної складності за Мак-Кейбом; опанувати технологію Data-Driven рефакторингу для повного усунення логічних розгалужень шляхом їх винесення у статичні структури даних (Lookup Tables); розгорнути локальні автоматизовані бар'єри якості (Quality Gates) на базі перехоплювачів Git Pre-commit Hooks для запобігання потраплянню заплутаного коду в репозиторій.

Інструментарій:
    • CLI Static Analyzers (на вибір під стек проєкту): Lizard CLI (pip install lizard), Radon CLI (pip install radon для Python), TyphonJS Escomplex (npm install -g escomplex-cli для JS/TS), PhpMetrics (для PHP) або Gocyclo (для Go).
    • Мультимовний стек (універсальний): Lizard CLI (через Python: pip install lizard).
    • JavaScript / TypeScript: TyphonJS Escomplex (через npm: npm install -g escomplex-cli).
    • PHP: PhpMetrics (через Composer або PHAR-архів).
    • Python: Radon CLI (через pip: pip install radon).
    • .NET (C#): Microsoft.CodeAnalysis.Metrics (через dotnet tool).
    • Примітка: Допускається використання інших безкоштовних CLI-сканерів, здатних розраховувати метрики Холстеда атомарно для файлів/методів.
    • Graph Visualization: Модуль діаграм Markdown Mermaid.js, Draw.io або Miro.
    • VCS Automation: Локальний рушій Git Hooks (папка .git/hooks/) або Python/Node.js pre-commit framework.

Об'єкт дослідження: Індивідуальний програмний проєкт студента. Аналіз проводиться на реальній кодовій базі без використання абстрактних абстракцій чи відірваних від контексту прикладів з інтернету.


ПОРЯДОК ВИКОНАННЯ ЗАВДАНЬ

Завдання 1. Первинний аналітичний скринінг репозиторію за Холстедом
Студент має провести комплексний лексичний аудит кодової бази за допомогою профільних консольних утиліт автоматизації, виявити приховані аномалії об'єму софту та довести неспроможність метрики LOC (рядків коду) як індикатора складності підтримки системи.

Покроковий алгоритм виконання:
        1. Інфраструктурне розгортання лінтера: 
Встановити у систему CLI-сканер відповідно до технологічного стеку свого індивідуального проєкту. Конфігурувати файли лінтера (якщо цього вимагає інструмент).
        2. Фіксація глобальної базової лінії (Global Baseline Scan): 
Запустити інструмент через термінал у корені проєкту та зняти сумарні первинні метрики Холстеда для всієї системи (загальний словник операторів й операндів):
    • – Кількість унікальних операторів (ключові слова, знаки операцій, роздільники).
    • – Кількість унікальних операндів (імена змінних, константи, рядки, аргументи).
    • – Сумарна кількість усіх операторів у тексті коду.
    • – Сумарна кількість усіх операндів у тексті коду.
Для детального аналізу обрати у своєму проєкті строго 3 різних за архітектурною роллю файли (мінімум 10–15 унікальних токенів у кожній функції). Такий вибір дозволить вам наочно порівняти, як архітектурна роль коду впливає на аналітичні зусилля розробника.
    • Файл 1: Модуль бізнес-логіки (Core Domain/Business Logic) – це сервіс, який виконує основну роботу системи: зосереджено багато розрахунків, перевірок, умов та обчислень. Приклади: Клас розрахунку вартості, двигун розподілу замовлень, модуль кошика, сервіс авторизації та перевірки прав.
    • Файл 2: Інтеграційний модуль (Integration / Infrastructure Layer) – файл, який відповідає за зв'язок вашого додатка із зовнішнім світом: за роботу із зовнішніми API, платіжними шлюзами або базою даних. Приклади: Модуль обробки відповідей від платіжного шлюзу (LiqPay/Stripe), клієнт для роботи з Telegram Bot API або кастомний репозиторій для складних SQL/NoSQL запитів.
    • Файл 3: Утилітарний або структурний файл (Utility/Helper/DTO) – необхідний як «контрольна група» для порівняння метрик. Приклади: Клас-валідатор рядків, хелпер для форматування дат, або об'єкт перенесення даних (DTO).
        3. Математична капіталізація метрик: 
Для кожного з 3-х файлів зняти первинні міри: унікальні оператори (η₁), унікальні операнди (η₂), сумарні оператори (N₁) та сумарні операнди (N₂). Розрахувати (або витягнути з розширеного логу CLI) похідні аналітичні індикатори Моріса Холстеда:
    • Словник програми: 𝜂=𝜂1+𝜂2
    • Довжина програми: 𝑁=𝑁1+𝑁2
    • Інформаційний об'єм програми (в бітах): 
    • Складність проєктування (індекс дефектності): 
    • Інтелектуальні ментальні зусилля розробника: 𝐸=𝑉×𝐷
        4. Ранжування аномалій (Hotspots Selection): 
На основі отриманих розрахунків проранжуйте файли/модулі вашого проєкту за показником ментальних зусиль розробника () від найбільшого до найменшого. Надати математичний доказ того, чому файл із меншою кількістю рядків коду (LOC), але високою щільністю унікальних токенів, вимагає більшого когнітивного навантаження на програміста.

Очікуваний результат завдання №1 у звіті
    • Декларація інструментального стеку: Повна офіційна назва та версія обраного CLI-інструменту статичного аналізу коду (SAST), а також точна консольна команда його ініціалізації та інсталяції в систему. Шлях до конфігураційних файлів лінтера (якщо використовуються, наприклад, .eslintrc.json, detekt.yml).
    • Глобальна базова лінія (Global Baseline Scan): Скріншот консольного виводу загального сканування всього репозиторію. Зведена таблиця сумарних первинних мір Холстеда для всього проєкту (загальний словник  та загальна довжина ).
    • Матриця архітектурного поштучного аналізу:
    • Порівняльна таблиця первинних (𝜂1, 𝜂2, 𝑁1, 𝑁2) та розрахованих за формулами похідних метрик (𝑉, 𝐷, 𝐸) для 3-х обраних файлів-представників архітектурних шарів:
    • Файл «Core Domain / Business Logic»;
    • Файл «Infrastructure / Integration Layer»;
    • Файл «Utility / Helper / DTO».
    • Локалізація аналітичних аномалій (Hotspots Selection) та інженерно-архітектурний висновок (Code Review): Виділений структурований перелік модулів проєкту, відранжованих за показником інтелектуальних зусиль розробника (). Короткий аналітичний коментар студента: як архітектурна роль коду вплинула на ментальні зусилля () та об'єм (), і чому сліпе вимірювання звичайних рядків коду (LOC) могло б приховати критичні проблеми в інтеграційному чи бізнес-модулі.

Завдання 2. Мапування графу CFG, математичний реверс-інжиніринг та Data-Driven рефакторинг
Перехід від лексичного аналізу слів до топологічного дослідження графів алгоритмів. Студент має навчитися керувати структурою коду на рівні точок прийняття рішень процесором.

Покроковий алгоритм виконання:
        1. Ізоляція базового стану коду (Baseline): 
Зробити стабільний коміт у Git. Обрати один метод із виявлених у Завд.1 складних файлів Core Domain або Infrastructure, який містить логічні розгалуження (if, else, switch, for, while). Зафіксувати його початкову цикломатичну складність () за допомогою CLI-сканера.
        2. Топологічне креслення графу CFG та математична верифікація Мак-Кейба:
Для обраного методу побудувати логічну карту – керуючий граф потоку виконання (Control Flow Graph) у Mermaid.js (код діаграми закласти у звіт) або Draw.io. Чітко виділити:
    • Вузли (Nodes) – лінійні оператори та команди.
    • Ребра (Edges) – стрілки переходів та передачі керування між командами.
    • Предикатні вузли – фізичні точки розгалуження логіки.

        3. Експеримент теоретичного розширення (FAIL-стан): 
Потрібно перевірити, чи здатна математична модель Мак-Кейба точно спрогнозувати складність коду, розробленого «на папері».
    • Дія: Графічно на кресленні графу CFG (пунктиром або іншим кольором) спроєктувати майбутнє розширення бізнес-правил алгоритму (додати 4 нові предикатні точки прийняття рішень та 6 ребер). Далі математично розрахувати на папері, якою стане цикломатична складність СС.
    • Створення FAIL-стану (Експеримент): Відкрити IDE і строго за кресленням дописати код однією монолітною функцією (з купою розгалужень if-else або switch-case, яка рахує якусь бізнес-опцію), щоб перетнути критичну індустріальну межу складності (CC>15).
    • Запустити CLI-сканер, звірити чи збіглося число автоматичного аналізу з його теоретичним розрахунком по графу. Якщо є розбіжності – знайти помилку у своїй математичній моделі та зафіксувати цей стан проміжним комітом у Git: feat(audit): simulate topological CC failure, FAIL.
        4. Data-Driven Refactoring та лінеаризація коду (PASS-стан): 
Повернути код додатка до стабільного стану (знизити цикломатичну складність до безпечного Enterprise-рівня: 𝐶𝐶≤10), але замість класичного подрібнення функції (Extract Method) застосувати передову техніку – Data-Driven Refactoring (Lookup Tables / Таблиці пошуку).
    • Суть рефакторингу: Повністю видалити з тексту методу весь хаос умов if-else або switch-case. Замість них створити статичну структуру даних – об'єкт-довідник (Map, Dictionary, Literal Object залежно від мови програмування), де ключами виступають умови, а значеннями – результати.
    • Результат: Метод перетворюється на лінійну функцію в 1–2 рядки, яка просто зчитує потрібне значення з довідника за ключем. Фізичні розгалуження зникають.
    • Валідація: Запустити повторне CLI-сканування. Переконатися, що цикломатична складність впала до абсолютного індустріального мінімуму (CC=1..2). Зафіксувати фінальний успішний статус PASS комітом у локальний Git: refactor(audit): eliminate conditional branches using lookup table, PASS.

Очікуваний результат завдання №2 у звіті
    • Початкова топологічна карта (Baseline): Графічна Mermaid-схема початкового стану обраного методу. Математичний розрахунок складності за формулою Мак-Кейба, підтверджений скріншотом консольного виводу CLI-сканера.
    • Модель теоретичного розширення логіки: Оновлена схема графу CFG, де графічно (іншим кольором або пунктиром) домальовано майбутні бізнес-правила та розгалуження алгоритму. Попередній «паперовий» математичний розрахунок цільового індексу складності.
    • Звіт про верифікацію математичного прогнозу (FAIL): Лістинг написаного монолітного коду, який строго реалізує спроєктоване креслення графу. Скріншот терміналу CLI-аналізатора зі статусом FAIL / перевищення ліміту (𝐶𝐶>15). Аналітичний коментар: чи збігся практичний розрахунок утиліти з вашою теоретичною моделлю (пояснення, як сканер зреагував на складні логічні оператори && чи ||).
    • Архітектурний кейс «Видавлювання розгалужень» (PASS): Наочне порівняння фрагментів коду «До» (хаос умов) та «Після» (Lookup Table / довідник даних) у вигляді лістингів або скріншотів Git Diff. Скріншот фінального сканування, що підтверджує падіння цикломатичної складності до мінімуму (CC=1..2) та статус GREEN / PASS.
    • Доказ лінійності Git-історії: Скріншот локального Git-графу (git log --oneline --graph), який чітко демонструє послідовність трьох обов'язкових станів репозиторію з валідними інженерними повідомленнями: Baseline  Simulated CC Failure (FAIL)  Lookup Table Refactoring (PASS).


Завдання 3. Локальна автоматизація «воротарів якості» через Git Pre-commit Hooks
Студент має налаштувати жорсткий інфраструктурний бар'єр якості безпосередньо на своїй робочій машині, який унеможливлює людський фактор (забудькуватість) та блокує потрапляння спагеті-коду в репозиторій додатка.

Покроковий алгоритм виконання:
        1. Конфігурація середовища перехоплювачів: 
Перейти у приховану директорію налаштувань локального репозиторію Git (.git/hooks/). Створити новий виконуваний файл pre-commit (суворо без розширення .sh або .txt). Для Unix-подібних систем надати файлу права на виконання через термінал: chmod +x .git/hooks/pre-commit (допускається альтернативне використання оркестратора pre-commit framework через конфіг .pre-commit-config.yaml).
        2. Скриптування валідатора складності: 
Написати автоматизований скрипт (Bash або PowerShell залежно від вашої ОС) для створеного файлу pre-commit. Скрипт повинен виконувати такі послідовні інженерні дії:
    • Автоматично виділяти список файлів, які розробник підготував до коміту (перебувають у Staged-стані після команди git add).
    • Проганяти виключно ці змінені файли через CLI-сканер складності коду.
    • Зчитувати Exit Code або парсити текстовий вивід сканера.
    • Якщо хоча б один метод у файлі, що йде в коміт, порушує встановлений архітектурний ліміт (CC>10), скрипт має вивести у термінал червоне попередження з описом аномалії та завершити роботу з системною помилкою Exit Code 1. Це змусить Git миттєво скасувати операцію створення коміту.
    • Якщо складність у нормі, скрипт повертає Exit Code 0, і коміт успішно створюється.
        3. Стрес-тест локального воротаря (Цикл FAIL  PASS): 
Продемонструвати працездатність хука викладачу на практиці.
    • Краш-тест (FAIL): Додати в код нову тестову функцію з глибокою вкладеністю умов, щоб її складність становила CC=12. Виконати git add та спробувати зробити коміт: git commit -m "feat: add messy code". Зафіксувати скріншотом терміналу, що Git-хук перехопив команду, запустив лінтер, вивів помилку і заблокував створення коміту (коміт не з'явився у git log).
    • Відновлення (PASS): Застосувати Data-Driven рефакторинг із Завд.2, переписати метод лінійно через довідник даних (CC=1..2), повторити git add та успішно виконати коміт. Зафіксувати безперешкодне створення коміту.

Очікуваний результат завдання №3 у звіті
    • Декларація скрипту автоматизації: Повний текст коду написаного скрипту pre-commit (або вміст файлу конфігурації .pre-commit-config.yaml).
    • Демонстрація перехоплення та блокування (FAIL): Скріншот вікна терміналу при спробі закомітити заплутаний код. На скріншоті має бути чітко видно команду git commit, вивід скрипта-хука з червоним попередженням про перевищення ліміту складності та системне повідомлення Git про скасування коміту.
    • Демонстрація успішного проходження (PASS): Скріншот терміналу після оптимізації коду, де видно, що команда git commit виконалася успішно, не зустрівши опору з боку сканера.

У підсумковому Project Hub-звіті студент повинен представити (Notion / Obsidian / тощо):
    • Декларація інструментального стеку: Назва, версія та точна консольна команда ініціалізації CLI-сканера.
    • Глобальна базова лінія Холстеда: Скріншот консольного виводу загального сканування репозиторію та таблиця сумарних мір для всього проєкту.
    • Матриця архітектурного поштучного аналізу: Зведена порівняльна таблиця первинних (η₁, η₂, N₁, N₂) та розрахованих похідних метрик (V, D, E) для 3-х різних за роллю файлів архітектурних шарів.
    • Топологічний паспорт алгоритму: Графічна схема графу CFG (Mermaid), математичний покроковий розрахунок складності вручну та скріншот консольного збігу з CLI-сканером.
    • Архітектурний кейс «Видавлювання розгалужень»: Порівняння фрагментів коду «До» (хаос умов, FAIL) та «Після» (Lookup Table, PASS) у вигляді лістингів або скріншотів Git Diff, а також скріншот фінального зеленого статусу Quality Gate.
    • Доказ лінійності Git-історії: Скріншот локального Git-графу (git log --oneline --graph), який чітко демонструє послідовність трьох обов'язкових станів репозиторію з валідними інженерними повідомленнями: Baseline  Simulated CC Failure (FAIL)  Lookup Table Refactoring (PASS).
    • Локальна автоматизація (Pre-commit Hook): Повний текст коду скрипту pre-commit, скріншоти консольного FAIL-блокування коміту при заплутаному коді та скріншот успішного PASS-проходження після рефакторингу.











КРИТЕРІЇ ОЦІНЮВАННЯ (Максимум: 10 балів)
Завдання 1 – 3 бали:
    • 3 бали: CLI-інструмент конфігурований та запущений у системі. Повністю зібрано базовий алфавіт та розраховано всі похідні метрики Холстеда для 3-х різних архітектурних шарів. 
    • 1.5 бали: Інструмент запущений, але аналіз проведено поверхово, або у звіті наведено сухі цифри з CLI без ранжування та без поштучного порівняння архітектурних файлів-представників.
    • 0 балів: Завдання не виконано, або дані повністю сфальсифіковані.
Завдання 2 – 4 бали:
    • 4 бали: Граф CFG побудовано без топологічних помилок, математичний розрахунок за формулою вручну повністю збігся з практичним консольним скануванням. У Git-історії чітко зафіксовано 3 послідовні стани проєкту (Baseline  FAIL  PASS). Рефакторинг виконано професійно за технологією Lookup Table, цикломатичну складність успішно знижено до мінімуму (CC=1..2).
    • 2 бали: Студент виконав завдання, але припустився помилок у кресленні графу CFG, або рефакторинг відбувся через просте дроблення методу (Extract Method) без винесення умов у структури даних. Або в Git-історії відсутній проміжний коміт зі статусом FAIL.
    • 0 балів: Завдання не виконано, або на момент демонстрації (Live Demo) утиліта фіксує перевищення складності.
Завдання 3 – 3 бали:
    • 3 бали: Скрипт Git pre-commit хука написаний коректно, повністю автоматизує виклик локального CLI-сканера для Staged-файлів додатка. Експериментально доведено працездатність системи: продемонстровано реальне блокування створення коміту (FAIL) при поганій якості коду та успішний пропуск (PASS) після рефакторингу алгоритму. Звіт містить усі необхідні скріншоти консолі та зрілий висновок.
    • 1.5 бали: Хук налаштовано, він викликає сканер, але не вміє зчитувати Exit Code (тобто сканер пише у консоль, що код поганий, але коміт все одно створюється, блокування фізично не працює). Або у звіті відсутні скріншоти консольного FAIL-блокування.
    • 0 балів: Завдання не виконано, локальна автоматизація відсутня.

Штрафні бали (при захисті у форматі Live Demo):
    • –2 бали: Студент не може пояснити різницю між Cyclomatic та Cognitive складнощами коду або плутає поняття операнда та оператора у метриці Холстеда.
    • –3 бали: Студент використав legacy-код/скрипти безпосередньо з інтернету без адаптації та розуміння його структури (плагіат).
