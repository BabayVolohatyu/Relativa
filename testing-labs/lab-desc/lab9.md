Завдання 1. Forensic-аудит SQALE-моделі Open-Source систем

Покроковий алгоритм виконання:
    1. Вибір об'єкта Forensic-аудиту:

Обрати один із великих активних open-source проєктів під свій мовний стек, який має значний обсяг кодової бази – чиста кількість фізичних рядків коду Lines of Code (ncloc) ≥ 50000. Зафіксувати точний унікальний ідентифікатор проєкту (project key та organization key) з URL-адреси.
    2. Програмне вивантаження SQALE-метрики через Cloud API: 
Виконати програмне GET-вивантаження параметрів моделі SQALE безпосередньо з глобальних хмарних серверів SonarQube Cloud за допомогою Postman або curl (для публічних проєктів API є повністю відкритим та безкоштовним).
    • Ендпоінт запиту: https://sonarcloud.io
    • Параметри: У полі component передати ключ обраного проєкту, а в полі metricKeys строго запитуйте три індикатори моделі SQALE та об'єму системи:

    • ncloc – чиста кількість фізичних рядків коду проєкту (без коментарів та пустих рядків).
    • sqale_rating – офіційний літерний рейтинг супроводжуваності системи за шкалою аналізатора.
Збережіть отриману сиру відповідь хмарного сервера у форматі JSON.
    3. Математична паспортизація тех.боргу за стандартом SQALE: 
Провести незалежний математичний аудит отриманого JSON-пакета для перевірки об'єктивності хмарних розрахунків:
    • Перевести загальний обсяг тех.боргу (sqale_index) із хвилин у чисті інженерні людино-дні (розділити хвилини на 60, а потім на 8 робочих годин в одному інженерному дні).
    • Розрахувати Індекс щільності технічного боргу (TDD) за класичною формулою стандарту SQALE. Для цього взяти отриманий обсяг людино-годин боргу і розділити його на повний час, необхідний для написання цієї кодової бази з нуля (який за стандартом SQALE вираховується як: ncloc * 30 хвилин / 60 хвилин):

    4. Верифікація хмарних розрахунків: 
Звірити отриманий відсоток TDD з офіційною індустріальною шкалою SQALE (Рейтинг А: ≤ 5%, Рейтинг B: 6%-10%, Рейтинг C: 11%-20%) та перевірити у звіті, чи збігається ваш розрахунок із літерною оцінкою sqale_rating, яку повернув хмарний сервер у JSON.

Завдання 3. Функціональне вимірювання розміру системи за методами FPA та Use Case Points
Студент має оцінити чистий об'єм корисної бізнес-функціональності софту, незалежно від мови програмування, для проведення зворотного калібрування реальної продуктивності інженерної команди.

Регламент та джерела отримання вихідних початкових даних:
Для унеможливлення суб'єктивного підбору цифр, студент зобов'язаний виділити в обраному Open-Source проєкті (із Завд.1) один конкретний ізольований бізнес-модуль (папку або набір із 3–5 взаємопов'язаних класів, наприклад: модуль автентифікації/RBAC, контролер обробки платіжних транзакцій, сервіс управління чергою сповіщень) та зібрати початкові дані з таких трьох джерел:
    • Початкові дані для категорії ДАНИХ (FPA): Витягуються безпосередньо зі структури даних обраного модуля – файлів конфігурації СУБД (Entity/Database Schema), моделей ORM, або сигнатур структур/типів даних, з якими взаємодіє код модуля.
    • Початкові дані для категорії ТРАНЗАКЦІЙ та АКТОРІВ (FPA & UCP): Витягуються із сигнатур публічних методів, API-ендпоінтів (HTTP GET/POST/PUT/DELETE маршрутів, прописаних у контролерах модуля) та інтерфейсів контрактів взаємодії класів.
    • Початкові дані для коефіцієнтів та калібрування (UCP & Git): Студент будує UML Use Case діаграму прецедентів для обраного підмодуля в Draw.io. Статистика трудовитрат (людино-годин) витягується ретроспективно з історії Git-логу цього підмодуля (git log --performance або підрахунком умовного часу розробки на основі кількості комітів та авторів, що створили ці класи).

Покроковий алгоритм виконання:
    1. Функціональний аналіз підмодуля за стандартом FPA (IFPUG): 
На основі зібраних початкових даних провести функціональну декомпозицію підмодуля у Google-таблицях:
    • Аналіз Даних: Визначити кількість Внутрішніх логічних файлів (ILF – власні сутності/таблиці, які модуль перезаписує) та Зовнішніх інтерфейсів (EIF – таблиці/API інших модулів, які зчитуються лише для довідки).
    • Аналіз Транзакцій: Підрахувати кількість Вхідних потоків (EI – операції створення/зміни даних через API), Вихідних обчислених потоків (EO – генерація звітів, калькуляцій) та Простих запитів (EQ – пряме зчитування даних на UI без трансформацій).
    • Присвоїти кожному елементу стандартну вагу складності (Простий/Середній/Складний) за міжнародним стандартом IFPUG та розрахувати підсумковий розмір підмодуля у Функціональних точках (FP).
    2. Оцінка розміру за методом Use Case Points (UCP): 
Провести паралельне об'єктно-орієнтоване вимірювання цього ж модуля за методикою Густава Карнера:
    • Розрахувати сумарну складність Акторів (UAW): Простий (зовнішнє API/CLI) = 1, Середній (протоколи TCP/HTTP) = 2, Складний (людина через GUI) = 3 бали.
    • Розрахувати складність Use Cases (UUCW) на основі кількості транзакцій (кроків логіки у сигнатурах методів): Простий (≤ 3 транзакції) = 5, Середній (4–7 транзакцій) = 10, Складний (> 7 транзакцій) = 15 балів.
    • Визначити базовий нескалібрований розмір UUCP = UAW + UUCW. Прийняти технічні (TCF) та екологічні (ECF) коефіцієнти як базові промислові (рівні 1.0), вирахувавши фінальний розмір у точках UCP = UUCP × TCF × ECF.
    3. Зворотне калібрування моделі продуктивності команди: 
Взяти зафіксований з історії Git-логу обсяг реальних трудовитрат (людино-годин), витрачених авторами на написання цього підмодуля (наприклад, сумарно 120 людино-годин). Алгоритмічно обчислити реальний Індекс продуктивності команди розробки (Productivity Factor – PF):

Сформулювати аналітичний висновок, як отриманий індекс PF дозволить компанії точно оцінювати вартість та бюджет майбутніх запитів на зміни (Change Requests) замовника ще до моменту написання першого рядка коду.

Очікуваний результат завдання №3 у звіті
    • Специфікація реверс-інжиніринг початкових даних: Перелік сигнатур методів, ORM-сутностей, Акторів та Use Case підмодуля, які виступали джерелом збору даних.
    • FPA Калькулятор (IFPUG Ledger): Таблиця розрахунку функціональних точок із зазначенням категорій (ILF, EIF, EI, EO, EQ), їхньої складності та фінального обсягу в точках FP.

    • Звіт про зворотне калібрування: Розрахунок індексу продуктивності команди (PF) у людино-годинах на одну UCP-точку та аналітичний висновок Lead Engineer про управління ризиками майбутніх Change Requests бізнесу.
    • Лог валідації ШІ-Техліда: Протокол проходження краш-тесту згідно з інструкцією.
