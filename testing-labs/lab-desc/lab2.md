Інженерія якості та супровід програмних систем 
ЛАБОРАТОРНА РОБОТА №2 
Вимірювана модель якості ISO/IEC 25010 
Performance Efficiency та Resilience Engineering 
Мета роботи: набути практичних навичок перетворення нефункціональних вимог 
продуктивності та надійності на вимірювані й автоматично перевірювані критерії; 
розроблення сценарію навантажувального тестування; експериментального дослідження 
поведінки системи в умовах відмови зовнішньої залежності; реалізації та автоматизованої 
верифікації механізмів стійкості програмного забезпечення. 
Загальна постановка завдання 
У межах лабораторної роботи необхідно перевести характеристики Performance 
Efficiency та Reliability моделі якості ISO/IEC 25010 у виконувану специфікацію якості 
(Executable Quality Specification), яка може бути перевірена за допомогою автоматизованих 
тестів. 
Для виконання роботи студент використовує програмний проєкт із Лабораторної 
роботи №1 або інший сервіс, який має щонайменше один HTTP API-ендпоінт і взаємодіє з 
базою даних чи зовнішньою залежністю. Код проєкту має бути доступним для модифікації, а 
сервіс — придатним до локального запуску та контрольованого створення навантаження. 
У результаті виконання роботи має бути реалізований повний цикл вимірювання та 
підвищення якості: 
Формалізація SLO → Навантажувальний тест → PASS/FAIL → 
Fault Injection → Фіксація відмови → Реалізація Retry/Fallback → 
Автоматизований Resilience Test → Підтверджена Graceful Degradation 
ФОРМА ЗДАЧІ ТА ЗАХИСТУ РОБОТИ 
1. Формат та регламент захисту (Live Demo) 
Захист лабораторної роботи відбувається виключно під час практичного заняття у 
форматі живої демонстрації екрана викладачу. Оцінка виставляється безпосередньо за 
результатами демонстрації та відповідей на запитання. На захист одного студента відводиться 
до 5 хвилин. Студент повинен заздалегідь запустити сервіс, тестові інструменти та всі 
необхідні залежності, щоб відразу перейти до демонстрації. 
2. Етапи демонстрації (чеклист для студента) 
Під час захисту студент повинен продемонструвати викладачу три ключові артефакти: 
▪  Крок 1. Performance SLO Validation. У терміналі запускається сценарій 
навантажувального тестування (k6, JMeter, Gatling або аналог). Студент показує 
встановлені порогові значення для p95 response time та Error Rate, а також два 
результати: успішний прогін зі статусом PASS і контрольований прогін зі статусом 
FAIL. 
▪  Крок 2. Fault Injection & Resilience Demo. Студент демонструє поведінку сервісу під 
час штучної затримки, timeout або відповіді HTTP 5xx від зовнішньої залежності. 
Необхідно показати стан до впровадження захисту та стан після реалізації Retry і/або 
Fallback, де система завершує запит контрольовано та не допускає каскадного 
аварійного завершення. 
▪  Крок 3. Code Review & Automated Resilience Test. В IDE демонструється код механізму 
стійкості, його параметри та автоматизований unit або integration test із mock/stub 
зовнішньої залежності. Тест повинен підтвердити Graceful Degradation і завершитися 
успішно. 
3. Умови успішного захисту 
▪  Якщо студент не може запустити навантажувальний сценарій або тест не містить 
автоматичних thresholds, Завдання 1 вважається виконаним частково. 
Інженерія якості та супровід програмних систем 
▪  Якщо демонструється лише код Retry/Fallback без відтворюваного сценарію відмови та 
порівняння поведінки «до/після», Завдання 2 не може бути оцінене максимальним 
балом. 
▪  Якщо resilience test не запускається або не перевіряє конкретний очікуваний результат, 
Завдання 3 відправляється на доопрацювання. 
ПОРЯДОК ВИКОНАННЯ 
Завдання 1. Performance Testing та валідація SLO 
Необхідно формалізувати вимоги до продуктивності критичної операції системи та 
реалізувати виконуваний сценарій навантажувального тестування, який автоматично визначає 
відповідність установленим SLO. 
Для виконання завдання студент повинен: 
▪  Обрати об’єкт тестування. Визначити один критичний HTTP API-ендпоінт або 
сервісну операцію. Описати її призначення, типовий запит, очікувану відповідь і 
залежності, які можуть впливати на час виконання. 
▪  Сформувати модель навантаження. Визначити кількість віртуальних користувачів, 
тривалість тесту, профіль зростання навантаження (ramp-up), частоту запитів і тестові 
дані. Модель повинна містити щонайменше два режими: нормальне та підвищене 
навантаження. 
▪  Реалізувати тестовий сценарій. Використати k6, Apache JMeter, Gatling або 
аналогічний інструмент. Сценарій має запускатися повторно однією командою та не 
вимагати ручного підрахунку результатів. 
▪  Визначити числові SLO. Налаштувати щонайменше два автоматичні критерії 
прийнятності: p95 response time ≤ X ms та Error Rate < Y %. Значення X і Y необхідно 
обґрунтувати з огляду на призначення операції та початкові вимірювання; 
використання лише довільних значень без пояснення не допускається. 
▪  Провести експеримент. Запустити тест за нормального навантаження та зафіксувати 
PASS. Далі контрольовано збільшити інтенсивність запитів або змінити threshold так, 
щоб інструмент зафіксував FAIL. Для обох прогонів зберегти p90, p95, p99, 
throughput/RPS та Error Rate. 
▪  Проаналізувати результати. Пояснити, який показник став причиною FAIL, де 
знаходиться фактичне вузьке місце та чому середній час відповіді не може замінити 
percentile-метрики p95/p99. 
Результат виконання завдання: відтворюваний сценарій навантажувального тестування з 
формалізованою моделлю навантаження, числовими SLO та автоматично зафіксованими 
станами PASS і FAIL, доповнений технічним аналізом отриманих метрик. 
Завдання 2. Resilience Engineering: Fault Injection та обробка відмов 
Необхідно експериментально дослідити поведінку системи при відмові зовнішньої 
залежності та реалізувати контрольований механізм підвищення стійкості, що запобігає 
некерованому падінню або каскадному поширенню помилки. 
Для виконання завдання студент повинен: 
▪  Визначити зовнішню залежність. Обрати базу даних, HTTP-сервіс, брокер 
повідомлень або інший компонент, від якого залежить обрана операція. Описати 
нормальну взаємодію та очікувану поведінку при недоступності компонента. 
▪  Реалізувати контрольований Fault Injection. За допомогою mock-сервера, proxy, 
тестової конфігурації або іншого відтворюваного способу створити щонайменше один 
сценарій: timeout/затримка або HTTP 5xx. Просте вимкнення всього застосунку не 
вважається коректною симуляцією відмови залежності. 
▪  Зафіксувати базову поведінку. Запустити сервіс без механізму захисту та 
задокументувати наслідок: Unhandled Exception, 500 Internal Server Error, перевищення 
Інженерія якості та супровід програмних систем 
допустимого часу очікування або іншу небажану реакцію. Зафіксувати статус, 
тривалість запиту та повідомлення в логах. 
▪  Обрати та впровадити resilience pattern. Реалізувати Retry з обмеженою кількістю 
повторів і затримкою між ними та/або Fallback із безпечною деградованою відповіддю. 
Параметри механізму повинні бути винесені в конфігурацію або чітко визначені в коді 
й технічно обґрунтовані. 
▪  Уникнути retry storm. Для Retry встановити максимальну кількість спроб, часові 
обмеження та backoff. Пояснити, чому нескінченні або синхронні повтори без затримки 
можуть погіршити стан перевантаженої залежності. 
▪  Підтвердити Graceful Degradation. Повторити той самий сценарій Fault Injection після 
внесення змін. Система повинна повернути передбачувану fallback-відповідь або 
контрольований статус, зберегти працездатність і сформувати діагностичний запис у 
логах. 
Результат виконання завдання: відтворюваний сценарій відмови зовнішньої залежності, 
реалізований у коді механізм Retry і/або Fallback та інструментально підтверджене 
покращення поведінки системи у форматі «до/після». 
Завдання 3. Автоматизація верифікації стійкості 
Необхідно покрити реалізований механізм обробки відмов виконуваним 
автоматизованим тестом, який захищає очікувану поведінку системи від регресій під час 
подальших змін. 
Для виконання завдання студент повинен: 
▪  Підготувати test double. Використати mock, stub, fake server або контейнеризовану 
тестову залежність, яка детерміновано відтворює timeout чи HTTP 5xx без ручного 
втручання. 
▪  Реалізувати позитивну перевірку. Підтвердити, що за нормальної відповіді залежності 
сервіс повертає очікуваний результат і механізм fallback не активується. 
▪  Реалізувати resilience test. Симулювати відмову та перевірити не лише відсутність 
exception, а конкретну очікувану поведінку: fallback-body, контрольований HTTP
статус, кількість retry-спроб і/або наявність діагностичного повідомлення. 
▪  Перевірити детермінованість. Запустити тест щонайменше тричі поспіль. Результат 
має бути стабільним і не залежати від доступності реального зовнішнього сервісу чи 
випадкових часових затримок. 
▪  Інтегрувати тест у проєкт. Додати його до загального набору автоматизованих тестів 
так, щоб він запускався стандартною командою test/build. У разі наявності CI 
допускається додатково продемонструвати успішне виконання в pipeline. 
Результат виконання завдання: стабільний автоматизований unit або integration test, який 
детерміновано моделює відмову зовнішньої залежності, підтверджує параметри механізму 
стійкості та гарантує збереження Graceful Degradation після рефакторингу. 
ВИМОГИ ДО ОФОРМЛЕННЯ ЗВІТУ 
Звіт повинен містити результати всіх етапів дослідження: 
Характеристика об’єкта дослідження 
▪  Призначення обраного сервісу та API-ендпоінту, технологічний стек, спосіб локального 
запуску. 
▪  Опис зовнішньої залежності та її ролі у виконанні операції. 
▪  Назва і версія інструмента навантажувального тестування. 
Performance Testing та валідація SLO 
▪  Код або конфігураційний файл тестового сценарію та команда його запуску. 
▪  Опис моделі нормального і підвищеного навантаження. 
▪  Обґрунтування thresholds для p95 response time та Error Rate. 
Інженерія якості та супровід програмних систем 
▪  Скріншоти або текстові результати прогонів PASS і FAIL; таблиця p90, p95, p99, RPS та 
Error Rate. 
Fault Injection та Resilience Engineering 
▪  Опис способу симуляції timeout або HTTP 5xx та підтвердження відтворюваності збою. 
▪  Фрагменти коду або Git diff «До» та «Після» впровадження Retry/Fallback. 
▪  Порівняння статусу, часу виконання та реакції сервісу до і після змін. 
Автоматизована верифікація стійкості 
▪  Лістинг resilience test і використаного mock/stub/fake server. 
▪  Результат щонайменше трьох послідовних успішних запусків тесту. 
▪  Підсумкова таблиця станів системи та короткий технічний висновок щодо відповідності 
характеристикам Performance Efficiency і Reliability моделі ISO/IEC 25010.

КРИТЕРІЇ ОЦІНЮВАННЯ (максимум: 10 балів) 
Завдання 1. Performance Testing та валідація SLO — 3,5 бала 
PASS 
▪  3,5 бала: Розроблено відтворюваний тестовий сценарій із двома режимами 
навантаження. Обґрунтовано щонайменше два числові thresholds. Інструмент 
автоматично фіксує PASS і FAIL. У звіті наведено p90, p95, p99, RPS, Error Rate та 
змістовний аналіз причини деградації. 
▪  2,5 бала: Сценарій працює й thresholds налаштовано, але модель навантаження або вибір 
граничних значень обґрунтовано поверхнево; частина метрик відсутня. 
▪  1,5 бала: Є робочий запуск навантажувального тесту, але немає автоматичного 
FAIL/PASS або наведено лише один режим навантаження. 
▪  0,5 бала: Продемонстровано лише ручні запити чи скріншоти без відтворюваного 
тестового сценарію. 
Завдання 2. Resilience Engineering та Fault Injection — 3,5 бала 
▪  3,5 бала: Реалізовано відтворюваний Fault Injection, задокументовано небажану 
поведінку «до», впроваджено й технічно обґрунтовано Retry і/або Fallback, 
продемонстровано Graceful Degradation «після» та відсутність каскадного падіння. 
▪  2,5 бала: Механізм стійкості працює, але параметри retry/backoff або fallback не 
обґрунтовано; порівняння поведінки до і після змін неповне. 
▪  1,5 бала: Додано обробку exception або статичний fallback, проте контрольований 
сценарій збою не відтворюється під час захисту. 
▪  0,5 бала: Є лише фрагмент коду чи конфігурації без демонстрації фактичної поведінки 
системи. 
Завдання 3. Автоматизований Resilience Test — 3 бали 
▪  3 бали: Написано стабільний unit або integration test із mock/stub, який симулює 
конкретну відмову, перевіряє очікуваний fallback/статус і параметри механізму 
Інженерія якості та супровід програмних систем 
стійкості, тричі поспіль завершується успішно та інтегрований у стандартний test/build 
процес. 
▪  2 бали: Тест автоматизований і працює, але перевіряє лише відсутність exception або не 
контролює кількість retry-спроб чи зміст fallback-відповіді. 
▪  1 бал: Тест формально присутній, але залежить від реального зовнішнього сервісу, 
працює нестабільно або потребує ручного втручання. 
▪  0 балів: Автоматизований тест стійкості відсутній або не запускається. 
Штрафні бали (під час захисту) 
▪  –2 бали: студент не може пояснити різницю між average response time та p95/p99 або не 
розуміє, як thresholds визначають PASS/FAIL. 
▪  –2 бали: Retry налаштовано без обмеження кількості спроб чи затримки, а студент не 
може пояснити ризик retry storm. 
▪  –3 бали: використано готовий код або тестовий сценарій без адаптації до власного 
проєкту та без розуміння його структури.
