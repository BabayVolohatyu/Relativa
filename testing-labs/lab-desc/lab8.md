ЛАБОРАТОРНА РОБОТА №8
Об'єктно-орієнтований аудит системного дизайну та інтерфейсна декомпозиція 
класів-мутантів (CK & MOOD Metrics)

Мета роботи: Набути практичних навичок комплексного інструментального аудиту та оптимізації якості об'єктно-орієнтованого системного дизайну програмного забезпечення; опанувати технологію автоматизованого видобутку архітектурних метрик та аналітичних логів у форматі JSON за допомогою програмних запитів до SonarQube REST Web API; навчитися інтерпретувати індикатори пакета Чидамбера-Кемерера (WMC, CBO, LCOM, DIT, RFC) та глобальні проєктні коефіцієнти MOOD Фернандо Абреу для формування об'єктивної базової лінії об'єктної структури проєкту; опанувати методику локалізації архітектурних аномалій та класів-мутантів за допомогою матриці зв'язності компонентів (Coupling Matrix); реалізувати повний інженерний цикл усунення антипатерну God Object шляхом інтерфейсної декомпозиції монолітної бізнес-логіки; навчитися проводити аудит вертикальних ієрархій за методологією Лоренца-Кіда та застосовувати техніку рефакторингу Replace Inheritance with Composition для мінімізації інфраструктурної крихкості програмних систем.

Інструментарій:
    • Analytical Metric Server: Платформа SonarQube Community Edition (локально розгорнута через Docker-контейнер на порту :9000) або хмарний акаунт SonarCloud Free Tier.
    • Automated REST Client: Інструментарій Postman або CLI-утиліта командного рядка curl (у Windows – PowerShell Invoke-RestMethod).
    • Architecture Visualization Tools: Профільні плагіни середовища розробки IDE для побудови Dependency Diagrams (MetricsReloaded, ArchUnit, VS Code Dependency Graph Extensions) або вебсервіс Draw.io/Miro.

Об'єкт дослідження: Індивідуальний програмний проєкт студента, який розвивається протягом семестру, або сторонній масштабний Open-Source проєкт з GitHub.


ПОРЯДОК ВИКОНАННЯ ЗАВДАНЬ
Завдання 1. Програмний видобуток ООП-паспортів системного дизайну через SonarQube REST Web API
Студент має виступити в ролі розробника засобів автоматизації контролю якості (Quality Tools Engineer). Замість ручного переписування цифр з графічного інтерфейсу, студент організовує автоматичне зчитування великих архітектурних даних безпосередньо з ядра сервера аналітики платформи SonarQube.

Покроковий алгоритм виконання:
    1. Актуалізація метричного зрізу: 
Запустити SonarQube (локально через Docker-контейнер на порту :9000) або хмарний акаунт SonarCloud (Free Tier). Переконатися, що файл конфігурації sonar-project.properties у корені проєкту налаштований правильно під мовний стек. Запустити в терміналі команду sonar-scanner для створення свіжого зрізу AST-дерева (Abstract Syntax Tree) системи.
    2. Програмна взаємодія з REST API SonarQube: 
Відкрити Postman або скористатися термінальною командою curl. Скласти та виконати прямий автоматизований HTTP-запит до офіційного ендпоінту сервера api/measures/component для 3-х ключових файлів вашої архітектури, визначених у ЛР№6 (Core Domain, Infrastructure та Utility/DTO).
Конфігурація ключів запиту: У параметрі metricKeys запиту строго передати індикатори об'єктного дизайну для вивантаження:
    • complexity / class_complexity – для аналізу зваженої насиченості методів класу (WMC за пакетом CK).
    • coupling_between_objects – для оцінки зачеплення класу з іншими об'єктами системи (CBO).
    • cohesion_in_methods / lcom4 – для аналізу браку внутрішньої згуртованості методів (LCOM).
Зберегти отримані сирі JSON-відповіді сервера. Знайти у структурі JSON числа метрик та занести їх до порівняльної таблиці у звіті.

Приклад curl-запиту:
curl -u YOUR_SONAR_TOKEN: http://localhost:9000/api/measures/component?component=my_project_key:src/domain/OrderProcessor.ts&metricKeys=class_complexity,coupling_between_objects,lcom4

    3. Збір глобальних проєктних коефіцієнтів MOOD: 
Шляхом виконання REST-запиту до компонентів вищого рівня або зчитування з аналітичного дашборду витягнути загальносистемні ООП-метрики всього репозиторію: коефіцієнти приховування методів та полів (MHF, AHF – відносні міри інкапсуляції у відсотках) та Coupling Factor (COF – загальний коефіцієнт зачеплення архітектури всього проєкту).
    4. Формування базової лінії (Baseline): 
Парсингом сирих JSON-відповідей сервера заповнити зведену архітектурну таблицю. Сформулювати первинний технічний вердикт щодо зрілості дизайну та наявності ознак спагеті-коду чи класів-мутантів.

Очікуваний результат завдання №1 у звіті
    • Декларація API-запитів: Лістинги виконаних HTTP-запитів (curl команди або скріншоти інтерфейсу Postman із прописаними URL-ендпоінтами) до Web API вашого сервера SonarQube/SonarCloud.
    • Аналітичний JSON-пакет: Фрагмент сирого тексту відповіді сервера у форматі JSON, де чітко видно числові значення об'єктних метрик (class_complexity, coupling_between_objects тощо) для ваших файлів.
    • Зведена таблиця CK & MOOD: Сформована на основі JSON-парсингу порівняльна таблиця метрик для 3-х різних за роллю файлів проєкту (Core Domain, Infrastructure та Utility/DTO) та загальних коефіцієнтів системи COF і MHF.
    • Первинний архітектурний вердикт: Лаконічний технічний висновок розробника щодо зрілості системного дизайну проєкту (виявлення ознак класів-мутантів чи спагеті-коду на основі отриманих чисел).


Завдання 2. Локалізація та ліквідація класів-мутантів (God Objects) через Coupling Matrix
Студент виступає в ролі Solution Architect. За допомогою інструментів візуалізації зв'язків він знаходить «епіцентр хаосу» в архітектурі системи та проводить радикальну хірургічну операцію з декомпозиції, закриваючи взаємодію об'єктів абстрактними контрактами.

Покроковий алгоритм виконання:
    1. Мапування епіцентру хаосу: 
Увійти у веб-інтерфейс SonarQube (вкладка Dependency Matrix / Coupling Matrix) або скористатися вбудованими плагінами IDE (наприклад: MetricsReloaded для IntelliJ, Dependency Graph для VS Code). Побудувати граф залежностей та локалізувати головну аномалію – клас-мутант (God Object), який безпосередньо взаємодіє з найбільшою кількістю інших файлів, і для якого Web API у Завд.1 видав критичні показники: CBO>15 та LCOM1. Зробити стартовий коміт у локальний Git, фіксуючи базову лінію об'єктного дизайну.

Модифікація умов при відсутності класу-мутанта: Якщо за результатами сканування у Завд.1 у вашому індивідуальному проєкті не виявлено класу з критичними показниками складності (CBO та LCOM в межах норми), виберіть один із двох інженерних шляхів для виконання Завд.2:
    • Метод штучної агрегації: Знайдіть у коді бізнес-логіку, яка «розпорошена» по різних файлах, та об'єднайте її в один монолітний клас, симулювавши появу God Object (FAIL), після чого проведіть його системний рефакторинг через інтерфейси.
    • Метод Open-Source консалтингу: Проведіть аудит і ліквідацію класу-мутанта на базі стороннього масштабного Open-Source проєкту з GitHub.

    2. Симуляція архітектурного колапсу (FAIL-стан): 
Провести краш-тест дизайну – продемонструвати ефект Shotgun Surgery («хірургія дробовиком»). Студент має спробувати внести одну невелику зміну в бізнес-логіку або сигнатуру методу будь-якого стороннього класу, від якого залежить God Object. Текстово чи логами звітів показати, що ця точкова зміна лавиноподібно ламає код у самому класі-мутанті через жорстке, монолітне зачеплення («привареність») до оточення. Зафіксувати цей стан як FAIL окремим комітом у Git: arch(audit): capture god object coupling failure, FAIL.
    3. Інтерфейсна декомпозиція системи (PASS-стан): 
Ліквідувати антипатерн на рівні об'єктної структури проєкту, застосувавши професійні техніки рефакторингу:
    • Повністю розбити один гігантський клас-мутант на 3–4 окремі, незалежні, дрібні класи, кожен з яких відповідає за одну ізольовану бізнес-задачу (принцип Single Responsibility).
    • Зв'язати нові класи між собою не напряму, а через абстрактні інтерфейси або контракти, впроваджуючи залежності через конструктор (принцип інверсії залежностей – Dependency Inversion / Dependency Injection).
    4. Інструментальна валідація відновлення: 
Запустити повторне сканування репозиторію через sonar-scanner та витягнути оновлені дані через Web API. Довести математично, що максимальний показник зачеплення окремого нового класу впав у безпечну зелену зону (CBO8, тобто новий клас пов'язаний не більше ніж із 8-ма іншими компонентами системи), а брак внутрішньої згуртованості методів наблизився до ідеалу (LCOM0.2). Зафіксувати успішний статус PASS комітом у Git: refactor(audit): eliminate god object via interface decomposition, PASS.

Очікуваний результат завдання №2 у звіті
    • Візуалізація початкового хаосу (Baseline Coupling Matrix): Скріншот матриці зв'язності (Coupling Matrix) з SonarQube або архітектурного графу залежностей з IDE, де чітко видно епіцентр хаосу – ваш клас-мутант із завеликою кількістю стрілок-зв'язків.
    • Протокол симуляції збою (FAIL): Лістинг коду, що демонструє ефект Shotgun Surgery – як дрібна зміна у сторонньому класі призвела до архітектурного зламу всередині God Object.
    • Специфікація декомпозиції (Архітектурний Blueprint): Схема нової структури системного дизайну, де показано, на які нові класи було розбито мутанта та через які інтерфейси налаштовано їхню взаємодію.
    • Фінальний аналітичний звіт (PASS JSON/Matrix): Оновлена таблиця метрик CK (WMC, CBO, LCOM), витягнута через Web API після рефакторингу, що математично доводить падіння показників до безпечних лімітів, та скріншот статусу GREEN / PASS.
    • Лог Git History: Скріншот дерева комітів Git, який наочно доводить наявність трьох послідовних станів репозиторію: Baseline  Captured God Object Coupling Failure (FAIL)  Interface Decomposition (PASS).





Завдання 3. Вертикальний аудит механізмів успадкування за Лоренцом-Кідом та деструкція Inheritance Hell
Дослідження об'єктної структури «по вертикалі». Студент має навчитися оцифровувати доцільність розширення коду та захистити архітектуру від антипатерну Inheritance Hell (Спадкове пекло), замінивши крихкі ієрархії гнучкою композицією.

Покроковий алгоритм виконання:
        1. Сканування вертикальних ієрархій (Baseline): 
Знайти у своєму проєкті ієрархічний ланцюжок класів, де використовується успадкування (extends або :). Витягнути через Web API або плагіни IDE метрику DIT (Глибина дерева успадкування) для цієї гілки. Підрахувати параметри Лоренца-Кіда для класу-нащадка: обсяг публічного інтерфейсу – Public Interface Size (PIM), та кількість перевизначених методів (Overridden Methods), які затирають логіку батьківських класів. Орієнтир аномалії: Глибина успадкування DIT3, великий показник PIM>20 та масове перевизначення методів свідчать про екстремальну крихкість дизайну. 
Примітка: При відсутності наслідування, студент штучно створює трирівневу ієрархію базових та дочірніх сервісів, де дочірній клас змушений переписувати половину логіки батьківських методів, симулювавши Baseline-стан.
        2. Симуляція каскадного руйнування ієрархії (FAIL-стан): 
Провести краш-тест вертикальних зв'язків. Внести зміну в сигнатуру або внутрішню логіку методу на найвищому рівні – у базовому батьківському класі. Документально (скріншотами з IDE чи помилками компілятора) продемонструвати, як ця точкова зміна автоматично «прострілює» по всьому ланцюжку наслідування донизу і каскадно ламає поведінку чи компіляцію класів-нащадків, змушуючи розробника аварійно правити код у дочірніх файлах. Зафіксувати цей збій як архітектурний FAIL комітом у Git: arch(audit): capture inheritance fragility crash, FAIL.
        3. Рефакторинг через композицію об’єктів (PASS-стан): 
Перепишіть архітектуру ієрархії, повністю розірвавши жорстку вертикальну залежність за класичним Enterprise-принципом: «Надавайте перевагу композиції об'єктів перед успадкуванням класів» (Replace Inheritance with Composition).
Дія: Видалити ключове слово успадкування (extends / :). Перетворити колишній батьківський клас на звичайне приватне поле всередині колишнього класу-нащадка (впровадити залежність через конструктор / Dependency Injection). Новий клас тепер просто делегує потрібні виклики внутрішньому об’єкту-помічнику.
        4. Фінальний аналітичний звіт: 
Запустити повторний аналіз коду. Довести за допомогою Web API SonarQube, що показник глибини успадкування для оптимізованого модуля впав до базового мінімуму (DIT=1), а кількість небезпечних перевизначених методів (Overridden) зменшилася до 0, повністю заізолювавши зміни. Зафіксувати статус PASS комітом у Git: refactor(audit): replace inheritance with composition pattern, PASS.

Очікуваний результат завдання №3 у звіті
    • Протокол первинного вертикального аналізу (Baseline): Опис ієрархії класів вашого проєкту, значення показника глибини наслідування DIT, підрахунок доданих та перевизначених методів за Лоренцом-Кідом.
    • Опис спадкового краш-тесту (FAIL): Документація того, як точкова модифікація батьківського класу призвела до каскадної регресійної помилки та падіння логіки дочірніх компонентів у стані FAIL.
    • Архітектурний кейс «Успадкування проти Композиції» (PASS): Лістинги коду «До» (наслідування через «extends» / «:») та «Після» (композиція об'єктів через Dependency Injection) з чітким коментарем, як змінився дизайн.
    • Фінальний аналітичний звіт: Математичне та інструментальне підтвердження того, що показник DIT успішно знизився до значення 1, а кількість Overridden методів тепер дорівнює нулю, з фіксацією статусу GREEN / PASS.
    • Лог Git History: Скріншот дерева комітів вашої робочої гілки із послідовністю трьох обов'язкових станів: Baseline  Capture Inheritance Fragility Crash (FAIL)  Replace Inheritance with Composition (PASS).

    • Архітектурний кейс «Успадкування проти Композиції»: Лістинги коду «До» (наслідування через extends / :) та «Після» (композиція об'єктів через Dependency Injection) з фінальним підтвердженням падіння метрики DIT до 1.
    • Логи Git History: Скріншоти дерева комітів Git для обох завдань, що наочно доводять наявність послідовностей станів: Baseline  FAIL  PASS з валідними інженерними повідомленнями.
    • Лог валідації ШІ-Техліда: Протокол проходження краш-тесту згідно з інструкцією.

Побудовано порівняльну таблицю шарів архітектури, сформульовано зрілий технічний вердикт за еталоном наскрізного кейсу.
