ЛАБОРАТОРНА РОБОТА №1
Автоматизований контроль якості програмного проєкту

Мета роботи: набути практичних навичок інтеграції засобів статичного аналізу в програмний проєкт, формалізації критеріїв якості, налаштування автоматизованої перевірки відповідності кодової бази визначеним вимогам та проведення повторної верифікації після внесення змін.

Загальна постановка завдання
У межах лабораторної роботи необхідно налаштувати автоматизований механізм контролю якості програмного проєкту на основі вимірюваних показників.
Для виконання роботи студент використовує існуючий програмний проєкт, що містить достатній обсяг вихідного коду для проведення статичного аналізу. Допускається використання власного навчального проєкту або іншого програмного проєкту, код якого студент має право модифікувати.
У результаті виконання роботи має бути реалізований повний цикл автоматизованого контролю якості:
Початковий аналіз → Визначення критеріїв → PASS →
Контрольоване порушення критеріїв → FAIL →
Усунення порушень → Повторний PASS

ФОРМА ЗДАЧІ ТА ЗАХИСТУ РОБОТИ
1. Формат та регламент захисту (Live Demo):
Захист лабораторної роботи відбувається виключно під час практичного заняття у форматі живої демонстрації екрана викладачу. Оцінка виставляється безпосередньо за результатами демонстрації та відповідей на запитання. На захист одного студента відводиться до 5 хвилин. Студент повинен заздалегідь розгорнути та запустити всі інструменти на своєму ноутбуці/комп’ютері, щоб відразу почати показ.
2. Етапи демонстрації (Чеклист для студента):
Під час захисту студент повинен продемонструвати викладачу три ключові артефакти:
    • Крок 1. Панель метрик та Quality Gate : Студент відкриває веб-інтерфейс аналізатора (SonarQube/SonarCloud тощо), де викладач має побачити фінальний успішний статус Quality Gate PASS (зелена зона). Студент усно коментує, які саме 4 критерії якості він налаштував у Завд.2.
    • Крок 2. Демонстрація історії змін: Студент відкриває свій локальний Git-репозиторій (через термінал, GitKraken, SmartGit або інтерфейс IDE) та показує історію комітів (Git History). Викладач має переконатися в наявності трьох послідовних станів проєкту:
    • Базовий стан (Baseline Scan).
    • Коміт із навмисними порушеннями (деградація якості), що призвів до стану FAIL.
    • Коміт із рефакторингом (відновлення до статусу PASS).
    • Крок 3. Code Review & Рефакторинг: Студент відкриває середовище розробки (IDE) і демонструє ділянку коду, яка була оптимізована в Завд.4 . Показує код «До» та «Після» рефакторингу, аргументуючи, за допомогою яких інженерних технік (наприклад, Extract Method, Guard Clauses) вдалося знизити Cognitive Complexity (≤ 15) та зменшити технічний борг системи.
3. Умови успішного захисту:
    • Якщо на момент захисту статус Quality Gate в аналізаторі має значення FAIL – робота автоматично відправляється на доопрацювання без подальшого розгляду.
    • Якщо студент не може наочно показати історію комітів або пояснити логіку проведеного ним рефакторингу в IDE – завд.№3 та №4 не зараховуються.


ПОРЯДОК ВИКОНАННЯ

Завдання 1. Інтеграція інструменту статичного аналізу коду (SAST)
Необхідно інтегрувати в обраний програмний проєкт інструмент автоматизованого статичного аналізу коду та налаштувати базовий процес сканування.
Для виконання завдання студент повинен:
    1) Обрати хмарний або локальний засіб статичного аналізу коду (SonarCloud, SonarQube Community Edition або аналогічний лінт-оркестратор, наприклад, Qodana).
    2) Конфігурувати інструмент під технологічний стек обраного проєкту.
    3) Налаштувати автоматичний запуск сканування кодової бази при кожному локальному збиранні або через базовий скрипт автоматизації.
    4) Провести первинне сканування проєкту (Baseline Scan) та зафіксувати метрики:
    • Security & Reliability: Загальна кількість Bugs та Vulnerabilities (із розподілом за критичністю: Blocker, Critical, Major).
    • Maintainability: Обсяг технічного боргу (Technical Debt) та кількість Code Smells.
    • Duplication: Відсоток дубльованого коду (Duplicated Lines %).
    • Complexity: Показники Cyclomatic та Cognitive Complexity.
    • Test Metrics: Рівень покриття коду тестами (Test Coverage %), якщо тести присутні.
    5) Внести мінімальну зміну в код (наприклад, додати коментар або форматування), запустити повторний аналіз та переконатися, що результати сканування успішно оновлюються.
Результат виконання завдання: Конфігураційні файли або скрипти інтеграції та розгорнутий засіб статичного аналізу (SAST), який у напівавтоматичному або автоматичному режимі виконує стабільне сканування проєкту, забезпечує коректне оновлення метрик при модифікації кодової бази та формує первинні вимірювані показники стану проєкту (Bugs, Vulnerabilities, Code Smells, Technical Debt, Duplications, Complexity, Coverage) для формування базової лінії (Baseline) якості.


Завдання 2. Формування та конфігурація Критеріїв якості (Quality Gate)
На основі метрик первинного сканування (Baseline Scan) розробити, обґрунтувати та впровадити стратегію автоматизованого контролю якості (Quality Gate), яка диференціює вимоги до історичного коду та нових змін у системі.
Для виконання завдання студент повинен:
    1) Створити кастомний профіль Quality Gate: У використовуваному інструменті (SonarQube/SonarCloud тощо) створити новий унікальний профіль критеріїв якості, відмінний від стандартного профілю за замовчуванням (Sonar way).
    2) Визначити та налаштувати не менше 4-х комбінованих критеріїв якості (Quality Gate Conditions): Для кожного критерію встановити конкретне граничне значення або допустиму умову. Критерії обов’язково мають бути розділені на дві категорії та покривати різні аспекти якості:
    • Категорія 1: Вимоги до нового коду (Conditions on New Code) – критерії, які перевіряють виключно той код, який додається або змінюється у межах поточної ітерації (наприклад, у Pull Request).
    • Обов’язковий критерій 1 (Надійність): Кількість нових критичних дефектів (New Bugs = 0).
    • Обов’язковий критерій 2 (Безпека): Відсоток перевірених вразливостей (New Security Hotspots Reviewed = 100%).
    • Категорія 2: Вимоги до всього коду (Conditions on Overall Code) – загальні ліміти для системи, що базуються на результатах первинного аналізу та не дозволяють проєкту деградувати нижче критичної межі.
    • Обов’язковий критерій 3 (Дублювання): Загальний відсоток дубльованого коду (Duplicated Lines % ≤ X%, де X визначається на основі первинного сканування, але не більше 5%).
    • Обов’язковий критерій 4 (Підтримуваність/Складність): Максимально допустимий індекс технічного боргу або когнітивної складності (Cognitive Complexity).
Наприклад:
    • New Code Reliability Rating = A (заборона нових багів).
    • Cognitive Complexity per Method ≤ 15.
    • Duplicated Lines % ≤ 3%.
    • Security Hotspots Reviewed = 100%.
    3) Надати архітектурне обґрунтування: Для кожного обраного критерію та його граничного значення (threshold) дати коротке технічне пояснення: чому саме цей показник є критичним для обраного типу архітектури чи технологічного стеку проєкту.
    4) Застосувати та верифікувати статус: Прив’язати створений Quality Gate до свого програмного проєкту, запустити повторний аналіз та отримати чіткий, зафіксований системою статус PASS або FAIL.
Результат виконання завдання: Сформована, архітектурно обґрунтована та активована в аналізаторі матриця критеріїв якості (Quality Gate Profile) із розділеними політиками для історичного та нового коду, яка успішно валідує поточний стан кодової бази з результуючим статусом PASS або FAIL.


Завдання 3. Симуляція деградації якості коду та верифікація тригерів Quality Gate
Експериментально перевірити чутливість налаштованої матриці критеріїв (Quality Gate), спровокувавши автоматичне блокування збирання через таргетоване порушення метрик як для нового, так і для загального коду.
Для виконання завдання студент повинен:
    1) Розробити план контрольованого збою: Навмисно внести до робочої гілки коду не менше двох незалежних архітектурних або логічних порушень, які гарантовано призведуть до невиконання критеріїв із Завд.2.
Приклади порушень: копіювання великого блоку коду (дублювання); створення методу з глибокою вкладеністю циклів/умов (скачок Cognitive Complexity); використання небезпечних функцій (Security Vulnerability); створення конструкції, що визначається аналізатором як Code Smell; зменшення рівня покриття тестами; створення Critical або Blocker Issue.
    2) Ініціювати сканування та зафіксувати FAIL: Запустити повторний статичний аналіз. Переконатися та документально зафіксувати за допомогою скріншотів, що:
    • Статус Quality Gate змінився на FAIL (червона зона).
    • Система чітко підсвітила, які саме критерії (метрика нового коду чи загального) стали причиною відхилення білду.
    3) Провести рефакторинг та відновлення (Fixing & Rollback): Усунути внесені порушення. При цьому студент має продемонструвати інженерний підхід: Bug має бути виправлений відповідно до правил Clean Code, а дубльований код – винесений в окремий багаторазовий метод/клас (рефакторинг), а не просто видалений.
    4) Верифікувати статус PASS: Провести фінальне сканування кодової бази та переконатися, що всі метрики повернулися в межі допустимих значень, а статус Quality Gate знову став PASS.
    5) Порівняти результати аналізу для трьох станів проєкту:
    • початковий стан;
    • стан після внесення порушень;
    • стан після їх усунення.
Результат виконання завдання: Успішно проведений стрес-тест системи контролю якості, під час якого зафіксовано спрацювання тригерів FAIL та продемонстровано повний цикл відновлення стабільності проєкту до статусу PASS шляхом рефакторингу та виправлення дефектів.


Завдання 4. Оптимізація архітектурної складності коду та управління технічним боргом
Набути практичних навичок аналізу та цілеспрямованого зниження технічного боргу системи, а також проведення рефакторингу коду з високим рівнем когнітивної складності (Cognitive Complexity) до значень, які відповідають стандартам Clean Code.
Для виконання завдання студент повинен:
    1) Ідентифікувати архітектурні аномалії (Code Smells & Debt): Використовуючи звіти аналізатора (розділи Maintainability та Technical Debt), знайти у своєму проєкті щонайменше два методи або класи з найгіршими показниками якості. Один із них обов’язково повинен мати критичний рівень когнітивної складності (наявність глибоких вкладених умов if-else, складних циклів, switch-конструкцій тощо).
    2) Проаналізувати метрику Technical Debt: Зафіксувати, як саме аналізатор розраховує технічний борг для цих ділянок коду (наприклад, у годинах/днях на виправлення чи через SQALE-індекс).
    3) Розробити та впровадити стратегію рефакторингу: Провести рефакторинг обраних проблемних ділянок коду, використовуючи класичні патерни та підходи чистого коду (Clean Code), щоб радикально спростити їхню структуру. Рекомендовані техніки: декомпозиція методів (Extract Method), заміна глибоких вкладених if на Guard Clauses (раннє повернення), позбавлення від дубльованої логіки, оптимізація алгоритмів.
    4) Досягти цільових архітектурних метрик: Після рефакторингу запустити повторний аналіз коду та продемонструвати:
    • Зниження індексу когнітивної складності (Cognitive Complexity) для модифікованих методів до прийнятного рівня (рекомендовано ≤ 15 для одного методу).
    • Реальне зменшення загального технічного боргу проєкту (Technical Debt) у часовому еквіваленті.
    5) Оформити архітектурний кейс (Code Review): У звіті навести порівняння фрагментів коду «До» та «Після» рефакторингу (у вигляді лістингу або скріншотів) та прокоментувати, за рахунок яких саме змін вдалося покращити оцінку аналізатора.
Результат виконання завдання: Продемонстрований процес успішного архітектурного рефакторингу програмного проєкту, підтверджений інструментальним аналізом: суттєве зниження когнітивної складності критичних методів та оптимізація (зменшення) загального обсягу технічного боргу системи.

Вимоги до результатів виконання (у звіті повинні бути представлені):
    1) Опис об’єкта дослідження:
    • Коротка характеристика обраного програмного проєкту (технологічний стек, призначення, орієнтовний обсяг кодової бази).
    • Назва, версія та спосіб розгортання/інтеграції засобу статичного аналізу (наприклад, SonarQube Community Edition локально через Docker або SonarCloud).
    2) Результати первинного аналізу (Baseline Scan):
    • Скріншоти та опис метрик стану кодової бази до внесення змін.
    • Зведена таблиця базових показників: Bugs, Vulnerabilities, Security Hotspots, Code Smells, Duplicated Lines %, Cyclomatic/Cognitive Complexity.
    3) Конфігурація та обґрунтування Quality Gate:
    • Скріншот налаштованого кастомного профілю критеріїв якості.
    • Перелік не менше 4-х обраних критеріїв.
    • Коротке архітектурне обґрунтування вибору кожного показника та встановленого для нього граничного значення (threshold).
    • Підтвердження успішного проходження початкової перевірки (статус PASS).
    4) Краш-тест системи (Симуляція збою):
    • Детальний опис та фрагменти коду (чи скріншоти) щонайменше двох навмисно внесених порушень.
    • Скріншот інтерфейсу аналізатора зі статусом FAIL, де чітко видно, які саме критерії було порушено та як змінилися метрики.
    5) Архітектурний рефакторинг та управління технічним боргом:
    • Опис двох ідентифікованих проблемних ділянок (методів або класів) із найвищим рівнем когнітивної складності або технічного боргу.
    • Наочне порівняння фрагментів коду «До» та «Після» рефакторингу (у вигляді лістингів коду або скріншотів GitHub/GitLab Diff).
    • Пояснення застосованих інженерних технік (наприклад, Extract Method, Guard Clauses тощо), які допомогли спростити код.
    6) Фінальна верифікація та порівняльний аналіз:
    • Скріншот фінального успішного статусу PASS після усунення всіх дефектів та проведення рефакторингу.
    • Заповнена підсумкова порівняльна таблиця для всіх станів проєкту (шаблон наведено нижче).
    • Короткий технічний висновок: аналіз ефективності метрики Cognitive Complexity порівняно з Cyclomatic Complexity, а також висновок про доцільність автоматичного контролю технічного боргу на реальних комерційних проєктах.

Завдання 1. Інтеграція інструменту статичного аналізу коду (SAST) – 2 бали
    • 2 бали: Інструмент успішно інтегровано. У звіті графічно (скріншотами) та текстово зафіксовано початковий стан кодової бази (Baseline). Описано всі базові метрики, аналізатор коректно оновлює дані при змінах.
    • 1 бал: Інструмент працює, але в звіті наведено лише сухі скріншоти без жодного аналізу чи текстового опису метрик.
    • 0 балів: Завдання не виконано або інструмент не налаштовано.
Завдання 2. Проєктування та налаштування Воротарів Якості (Quality Gate) – 3 бали 
    • 3 бали: Створено кастомний профіль Quality Gate (не менше 4-х критеріїв) із правильним розподілом на New Code та Overall Code. У звіті наведено чітке архітектурне обґрунтування для кожного граничного значення (threshold). Зафіксовано початковий статус PASS.
    • 2 бали: Критерії налаштовано, але у звіті відсутнє аналітичне обґрунтування лімітів (виставлені «наосліп»), або критерії не розділені на новий та історичний код.
    • 1 бал: Налаштовано менше 4-х критеріїв, логіка роботи профілю описана поверхнево.
Завдання 3. Симуляція деградації якості коду та верифікація тригерів – 2.5 бали
    • 2.5 бали: Чітко задокументовано (код + скріншоти) внесення 2-х незалежних порушень для різних типів умов. У звіті відображено перехід у FAIL із зазначенням конкретної причини, а також процес виправлення та фінальний PASS.
    • 1.5 бали: Продемонстровано роботу тригерів, але внесено лише один тип порушення, або етап відновлення коду описано неповністю.
    • 0.5 бала: Отримано FAIL, але процес рефакторингу та повернення до PASS у звіті не зафіксовано.
Завдання 4. Оптимізація архітектурної складності та управління тех. боргом – 2.5 бали 
    • 2.5 бали: В межах звіту наочно продемонстровано архітектурний кейс (Code Review у форматі «До/Після»). Інструментально доведено зниження Cognitive Complexity (≤ 15) та зменшення тех.боргу. Додано фінальну порівняльну таблицю станів та глибокий технічний висновок про різницю між когнітивною та цикломатичною складністю.
    • 1.5 бали: Рефакторинг проведено, але когнітивна складність залишилась високою, або «виправлення» відбулося шляхом видалення коду. Порівняльна таблиця заповнена, але висновок формальний.
    • 0.5 бала: Код змінено, але немає порівняльних метрик, таблиці станів або технічного висновку.

Штрафні бали (при захисті):
    • –2 бал: Студент не може пояснити різницю між Cyclomatic та Cognitive складнощами коду під час усної відповіді.
    • –3 бал: Використано legacy-код безпосередньо з інтернету (плагіат) без жодної спроби адаптації чи розуміння його структури.
