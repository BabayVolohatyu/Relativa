# Helm простими словами (файл лише для мене)

Це шпаргалка, щоб зрозуміти, що ми зробили в Лабі 4, навіщо, і як це розповісти викладачу. Це не частина звіту.

## 1. Що таке Helm

Уяви, що Kubernetes це операційна система для контейнерів, а YAML-маніфести це файли, з яких вона збирає застосунок. У Лабі 3 в мене було 9 таких файлів у `k8s/`. Щоб поставити застосунок, я робив `kubectl apply -f k8s/`. Проблеми:

- Значення (кількість реплік, тег образу, порт) зашиті прямо у файли. Хочу іншу кількість реплік для prod, значить копіюю файли і правлю.
- Kubernetes не знає, що ці 9 об'єктів є одним застосунком. Видалити, оновити і відкотити можна лише по одному об'єкту.
- Немає історії: що було до зміни, не відомо (крім git).

Helm вирішує це. Це «apt/npm для Kubernetes», тільки для твого власного застосунку:

| Поняття | Аналогія |
|---|---|
| Чарт (chart) | пакет, інсталятор: шаблони + значення за замовчуванням |
| values | налаштування інсталятора |
| Реліз (release) | конкретне встановлення цього пакета під іменем (`relativa`) |
| Ревізія (revision) | номер версії встановлення, як коміт для релізу |
| `helm install/upgrade/rollback/uninstall` | встановити, оновити, відкотити, видалити весь застосунок одним махом |

## 2. Helm чи kubectl

| | kubectl apply | Helm |
|---|---|---|
| Одиниця керування | окремий об'єкт | реліз (група об'єктів) |
| Параметри | правиш YAML | `values.yaml`, `-f`, `--set` |
| Історія | немає | `helm history` |
| Відкат | вручну | `helm rollback` |
| Видалення | кожен об'єкт окремо | `helm uninstall` |
| Кілька середовищ | копії файлів | один чарт, різні values |

Helm не замінює kubectl, а працює поверх нього: усередині він теж створює Deployment, Service тощо.

## 3. Що ми робили і навіщо

2. Підняли minikube і видалили реліз Лаби 3, щоб почати з чистого кластера.

4. Перенесли маніфести в шаблони. Усе, що раніше було числом чи рядком (репліки, тег, ресурси, порт), замінили на `{{ .Values.… }}`. Навіщо: щоб змінювати налаштування, не чіпаючи шаблони.

8. `helm lint` (перевірка), `helm template` (подивитися готові маніфести без кластера), `helm install` у namespace `relativa-helm`.
9. Життєвий цикл: `upgrade` через `--set` (ревізія 2), через prod-файл (ревізія 3), `rollback` до 1 (ревізія 4), `uninstall`. Навіщо: показати, що Helm пам'ятає історію і вміє відкочувати.
10. Завдання на вибір: хук `pre-upgrade` (перевірка БД перед оновленням) і `helm test` (перевірка `/health`). Навіщо: показати, що Helm може виконувати дії на етапах життєвого циклу.

## 4. Пояснення для викладача (приблизно 2 хвилини)

> У Лабі 3 я розгортав Relativa у Kubernetes набором YAML-файлів через kubectl. У Лабі 4 я запакував це в Helm-чарт. Чарт складається з шаблонів, у яких усі налаштування (кількість реплік, тег образу, ресурси, розмір диска, чи вмикати Ingress) винесені у `values.yaml`. Для prod є окремий файл значень: 3 репліки, образ 1.1.0, Ingress увімкнено. Пріоритет такий: `values.yaml` найнижчий, потім `-f`, потім `--set`.
>
> Я встановив реліз командою `helm install` у власний namespace, який Helm створив сам через `--create-namespace`. Namespace не в шаблонах, бо Helm зберігає стан релізу саме в цьому namespace, тож він має існувати раніше. Далі я оновив реліз двічі: змінив тег образу через `--set` і застосував prod-значення. Кожна зміна створила нову ревізію. Потім зробив `helm rollback` до першої ревізії, і Helm створив четверту ревізію зі старими значеннями. Історія показує всі кроки, а `helm get values --revision` показує значення кожної ревізії.
>
> Як завдання на вибір я зробив хук `pre-upgrade`, який перед оновленням перевіряє через `pg_isready`, що база відповідає, і `helm test`, який перевіряє `/health`. Щоб показати користь хука, я навмисно вказав неправильний порт бази: апгрейд зупинився з помилкою, ревізія 5 стала failed, а застосунок продовжив працювати без змін. Після цього я відкотився, і з'явилась ревізія 6.
>
> Стан релізу Helm зберігає як Secret типу `helm.sh/release.v1`, по одному на ревізію. Після `helm uninstall` у namespace не лишилось нічого, крім `kube-root-ca.crt`, який Kubernetes створює сам.

## 5. Підводні камені (на які я натрапив, і про які можуть спитати)

- Helm 4 і Helm 3 відрізняються. Лаба для Helm 3, тому поставлено 3.20.0.
- Pod'и хуків (і тестів) не належать до релізу, тому `helm uninstall` їх не видаляє. Тому в політиці видалення є `hook-succeeded`, а невдалий Pod хука довелось видалити вручну.
- `kube-root-ca.crt` після uninstall це нормально: його створює Kubernetes, а не Helm.
- Розмір PVC у prod не міняли: PVC не зменшується, а розширення залежить від storage class, тож upgrade міг би впасти.
- Відкат створює нову ревізію, а не повертає стару. Тому в історії 6 рядків, хоч «змістовних» змін було менше.
- Реальні паролі не кладуться у values. У репозиторії лише синтетичні значення, а шаблон використовує `required`.
- Docker Desktop одного разу завис. Допомогло: закрити Docker, `wsl --shutdown`, запустити знову.
- Ревізія 5 failed лишається в історії назавжди. Це нормально, це доказ того, що хук спрацював.

## 6. Що я маю вміти показати руками

```text
helm lint helm/
helm template relativa helm/ -f helm/values-prod.yaml | Select-String replicas
helm install relativa helm/ -n relativa-helm --create-namespace --wait
helm upgrade relativa helm/ -n relativa-helm --set gateway.image.tag=1.1.0 --wait
helm history relativa -n relativa-helm
helm rollback relativa 1 -n relativa-helm --wait
helm test relativa -n relativa-helm
helm uninstall relativa -n relativa-helm
```

Увесь цей цикл автоматизовано в `devops/defence/lab4/run-lifecycle.ps1`, а результати лежать у `devops/evidence/lab4`. Якщо живий показ не вдасться, відкрию ці файли.

## 7. Мінімум, який треба запам'ятати

- Helm = менеджер пакетів для Kubernetes: чарт + values = реліз.
- Шаблони дають гнучкість, values дають налаштування, ревізії дають історію і відкат.
- Пріоритет значень: values.yaml < `-f` < `--set`.
- Хук виконується на етапі життєвого циклу, `helm test` перевіряє, що реліз працює.
- Стан релізу це Secret у кластері, окремого сервера (Tiller) у Helm 3 немає.
