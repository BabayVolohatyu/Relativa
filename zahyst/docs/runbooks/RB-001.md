# RB-001. Дамп PostgreSQL і перевірка відновлення

Ідентифікатор: RB-001. Операція: зняти повний дамп бази Relativa і довести, що він розгортається в окрему базу `relativa_drill`.

Рівень автоматизації обраної операції (дамп і drill в окрему базу): 1, скриптований. До коміту реалізації RFC-001 ті самі команди виконуються з розділу «Кроки» руками. Після коміту їх викликають `ops/pg-dump.ps1` і `ops/pg-restore-drill.ps1`. Відновлення поверх основної бази лишається рівнем 0: це ручне рішення чергового, бо автоматичний restore перезаписав би живі рядки. Self-healing тут шкідливий. «Одна кнопка» теж рано: немає розкладу і копії поза машиною.

## Тригер

Один із алертів каталогу нижче: `BackupStale`, `PostgresVolumeMissing`, `MigrationExitNonZero`. Планове розкладання — раз на добу, навіть якщо алерт мовчить. Скарга «після `docker compose down -v` дані зникли» веде сюди ж.

## Передумови

- Контейнер `relativa-postgres` у стані healthy. Образ `postgres:16-alpine`, том `postgres_data`.
- Файл `.env` у корені. Скрипт читає `DB_NAME`, `DB_USER`, `DB_PASS`. Пароль у звіт і в git не потрапляє.
- Docker CLI на машині чергового. Окремого логіна в хмару немає: це стенд Compose.
- Каталог `backups/` у корені. Він у `.gitignore`.

## Кроки

З кореня репозиторію, контейнер `relativa-postgres` уже healthy. Ім'я бази і користувач — з `.env` (`DB_NAME`, `DB_USER`). Нижче значення стенда з `.env.example`.

Дамп у файл усередині контейнера і копія на хост:

```text
docker exec relativa-postgres pg_dump -U relativa -d relativa -Fc -f /tmp/relativa.dump
docker cp relativa-postgres:/tmp/relativa.dump backups/relativa.dump
```

Перевірка відновлення в окрему базу, не в `relativa`:

```text
docker exec relativa-postgres psql -U relativa -d postgres -c "DROP DATABASE IF EXISTS relativa_drill"
docker exec relativa-postgres psql -U relativa -d postgres -c "CREATE DATABASE relativa_drill"
docker cp backups/relativa.dump relativa-postgres:/tmp/relativa.dump
docker exec relativa-postgres pg_restore -U relativa -d relativa_drill --no-owner /tmp/relativa.dump
```

RFC-001 загортає ці чотири команди в `ops/pg-dump.ps1` і `ops/pg-restore-drill.ps1`. Поки скриптів немає в дереві, черговий виконує команди з цього розділу сам. Рівень лишається 1, щойно скрипти з'являються: рішення «заливати в основну базу» скрипт не приймає.

## Верифікація

Drill завершується з кодом 0, а в лозі є рядок `drill_ok` і число таблиць `public` у `relativa_drill` дорівнює числу таблиць `public` у основній базі. Файл дампа лежить у `backups/` і не старший за 24 години.

`GET http://localhost:8080/health` після drill лишається `status=ok`: drill не чіпає порт 8080 і не перемикає застосунок на `relativa_drill`.

## Відкат

Drill-база зайва або відновлена криво:

```text
docker exec relativa-postgres psql -U relativa -d postgres -c "DROP DATABASE IF EXISTS relativa_drill"
```

Основну базу ця команда не видаляє. Відкат дампа, який уже залили поверх основної бази, у цьому runbook заборонений без окремого RFC: спочатку новий дамп поточного стану, потім рішення CCB.

Відкат коду скриптів — `git revert` коміту, який їх додав. Схема бази від скриптів не змінюється.

## Ескалація

| Умова | Кому | Таймаут |
|---|---|---|
| Дамп не знявся | черговий L2, власник Migration | 15 хвилин від старту скрипта |
| Том `postgres_data` відсутній і дампа немає | L3, власник ISD | одразу, це SEV-1 |
| `/health` не `ok` після відновлення основної бази | L2 Gateway, паралельно L3 | 10 хвилин |

Каталог ролей L1–L3 — у плані супроводу. Поки план не опублікований, L2 — автор міграцій, L3 — власник `docs/architecture/isd.md`.

## Каталог алертів

Окремого Prometheus у репозиторії немає. Умови нижче перевіряються скриптом дампа, кодом виходу контейнера `migration` і `docker volume ls`. Алерт без рядка в цій таблиці черговому не ставиться.

| Назва | Умова | Серйозність | Роль | Runbook |
|---|---|---|---|---|
| BackupStale | Немає файлу `backups/relativa-*.dump` або найновіший старший за 24 години | SEV-2 | SRE / L2 | RB-001 |
| PostgresVolumeMissing | `docker volume ls` не містить `postgres_data` або `pg_isready` у контейнері падає тричі поспіль | SEV-1 | SRE / L3 | RB-001 |
| MigrationExitNonZero | Контейнер `relativa-migration` завершився з кодом, відмінним від 0 | SEV-1 | L2 Migration | RB-001 |
